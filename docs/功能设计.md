<a id="position"></a>
## 1. 名称与定位

- 产品名称：ExKeyGate。
- 中文名称：ExKeyGate 密钥认证管理服务。
- 工程名称：`ex-keygate`。
- 定位：支持插件扩展、客户端共享密钥管理和多人授权的轻量认证服务。

ExKeyGate 为客户端提供统一认证入口，底层既可以接入第三方密钥服务，也可以使用内部密钥实现。关键密钥操作通过多人审批执行，并保留完整审计记录。

服务只承担身份认证、密钥生命周期管理和相关审批，不承接各业务系统的业务权限判断。

<a id="principles"></a>
## 2. 设计原则

1. 一个工程、一个仓库，交付同一服务程序；支持部署多个节点，不依赖单进程内存保证安全正确性。
2. 建议以 Go 实现服务端，对外接口和扩展协议保持语言中立。
3. 内部实现和第三方能力通过统一 Provider 接口接入。
4. 多人授权由主服务统一控制，插件不能绕过审批。
5. 密钥异常时可以明确定位影响范围，并停用、轮换和恢复。
6. 保持第一版简单，不引入微服务拆分、插件热加载和复杂工作流。
7. 安全优先于接入便利和功能数量；简化部署不能省略关键安全控制。

### 安全目标与边界

用户要求以最高安全要求设计。本文将其落实为可验证的安全基线及增强目标，不宣称绝对安全或已获得安全认证。编码前需要明确威胁模型，至少覆盖网络攻击、客户端泄露、数据库及备份泄露、管理员账号失陷、恶意插件、审批绕过、重放及服务器失陷。

只有软件实现时，不能保证服务器被完全控制后密钥仍不可提取，也不能保证存放在不受控客户端中的共享密钥不被提取。多人业务审批不能单独阻止服务器管理员直接修改程序或数据库。需要抵御这些威胁时，必须进一步采用受保护的硬件密钥、独立执行授权或等效隔离方案。

真实硬件接入仍按用户要求暂缓。未完成硬件实现和验证前，只能验收软件安全基线，不能宣称已经达到硬件保护或密码学门限授权目标。

<a id="concepts"></a>
## 3. 核心概念

| 概念 | 含义 |
| --- | --- |
| 客户端 | 使用密钥参与认证的应用、设备或服务，具有唯一 clientId |
| 客户端共享密钥 | 客户端与认证服务共同使用的认证凭据，按客户端绑定并管理版本 |
| 基础密钥 | 内部用于保护其他密钥或支撑底层认证能力的密钥，原则上不下发客户端；具体用途待确认 |
| Provider 插件 | 提供密钥或认证能力的实现，包括内部实现及第三方适配 |
| 授权策略 | 规定操作需要哪些人员、多少人批准及有效时间 |
| 审批申请 | 绑定具体目标和操作内容的一次授权流程 |
| 审计记录 | 对管理、审批和执行行为的可追溯记录 |

本文暂按“多人授权等于 M/N 人工审批”设计，例如 3 名授权人中至少 2 人同意。密钥分片和门限密码学属于不同方案，未纳入第一版承诺。

<a id="features"></a>
## 4. 功能清单

### 4.1 客户端管理

- 创建客户端，分配唯一 clientId。
- 维护名称、用途、负责人及备注。
- 绑定认证方式、Provider 和对应密钥。
- 覆盖后端、桌面、移动端及浏览器，按客户端类型独立配置认证策略；类型由受控管理流程登记，请求不能自行切换为更弱策略。
- 浏览器不默认保存长期共享密钥，桌面和移动端也不预设静态嵌入密钥可信；具体协议按类型另行设计。
- 查询客户端状态及关联密钥版本。
- 启用或停用客户端；停用后拒绝后续认证。
- 不同客户端默认使用独立密钥，避免一个密钥异常影响所有客户端。

### 4.2 密钥生命周期管理

- 使用内部 Provider 创建密钥。
- 接入第三方密钥引用；原始密钥是否可导入或导出取决于 Provider 能力及授权策略。
- 查看密钥标识、来源、关联客户端、版本、状态及有效期。
- 创建新版本并执行轮换。
- 配置新旧版本并行有效的过渡期，过渡期结束后旧版本失效。
- 停用泄露、失效或不再使用的密钥。
- 记录停用原因和审批关联信息。
- 默认不提供日常查询密钥明文的功能；需要下发的共享密钥采用受控交付，具体方式待确认。

密钥状态沿用阶段 1：pending（待交付/确认）、staged（已证明持有）、active（有效）、retiring（过渡期）、disabled（普通停用）、expired（到期）、compromised（泄露撤销）。审批结果、执行结果和密钥状态分别展示。compromised 已实现专用应急撤销、事件账本和数据库终态保护；本批操作与恢复入口见[生命周期运行手册](生命周期运行手册.md)。

<a id="rotation"></a>
#### 4.2.1 密钥轮换补充

当前已有开发基础：创建新版本、独立领取及持有证明、再次审批激活、原子新旧切换、最多一个 active 和一个 retiring、最长十五分钟开发过渡期，以及按数据库时间拒绝失效版本。现已补齐轮换任务关联、原因、原期限可信标记、页面到期提示、每分钟自动过期收尾及显式维护入口；没有创建外部通知或自动执行审批操作。

- 轮换申请固定环境、客户端、旧新版本、目标修订、接收方两把公钥指纹、截止时间和原因；计划变化必须新申请，不继承旧票。轮换不修改旧版本秘密。
- 到期提醒只生成通知或待处理事项，不自动签发、领取或激活。提醒提前量及生产周期由受控配置决定，不把开发的 24 小时有效期当作生产默认。
- 新版本未完成交付和持有证明时不切换；激活仍单独多人审批。多个节点重复触发、相同申请重试及并行轮换不能产生多个有效新版本。
- 保存原有效期与批准的退役截止信息；旧版最终可认证期限取二者较早值。截止按数据库时间立即生效，后台收尾仅更新展示状态和通知，不能成为拒绝旧版认证的前提。
- 新版本切换前失败，只允许旧版在原有合法期限和状态下继续使用。新版本启用后异常，不自动恢复已停用、撤销或过期的旧版，也不自动延长过渡期；需应急收紧并重新审批新方案。
- 操作视图串联轮换申请、签发、领取、持有证明、激活、旧版退役和各自审计。不得以 approved 或 execute 成功替代整次轮换完成。

验收：切换前旧版有效/新版拒绝；批准过渡期内两版按策略有效；截止后旧版拒绝、新版正常；任务停机仍按时拒绝旧版；并发切换、重复执行和失败回退均不复活无效版本。

<a id="revocation"></a>
#### 4.2.2 密钥撤销补充

当前已有正常 key_disable 审批及整个客户端的应急停用。已实现按版本泄露撤销、根关联阻断、事件账本、终态保护和开发隔离恢复。

| 情形 | 目标行为 | 恢复边界 |
| --- | --- | --- |
| 正常不再使用 | 原申请人提交停用，独立多人批准后执行 | 不直接恢复原版本；重新签发与审批 |
| 版本疑似或确认泄露 | 范围内应急人员立即标为 compromised，记录事件编号、原因和受影响版本 | 原版本永久不可恢复；误报也不解除该版本撤销 |
| 影响边界不清 | 先停用整个客户端，核对所有版本、接收方和正在执行的申请 | 保持普通认证关闭，通过隔离恢复任务准备并验证新凭据，最后独立审批并原子恢复；使用 recovery_issue 与 recovery_activate 两个独立审批流程 |
| 根密钥泄露 | 阻断该根用途，立即影响其全部依赖版本，记录处置范围 | 同根保护的客户端秘密视为可能泄露；单纯重包裹原秘密不算恢复，需可信新根和新客户端秘密 |

- 应急权限只能减权，不允许导出、激活、恢复、替换接收方或降低阈值。保存操作者、范围、原因码及事件关联；长文本不得未经处理直接进入日志。
- 权威撤销、目标修订、撤销事实和本地审计同事务提交，提交后新开始的认证拒绝。已完成认证的业务操作不追溯取消；外部高敏感业务的执行时复查需在接入时单独实现。
- 先阻断根或客户端的权威状态，再进行关联版本批量标记，不能等全部批处理或外部通知成功后才阻断。外部告警可可靠重试，本地留痕失败不得假报撤销成功；权威库不可用时现有认证继续失败关闭。
- 备份回滚、旧节点接管、过期审批及晚到 Provider 响应不得清除撤销事实。撤销事实需要独立可信校验点，不能只保存在同一份可回滚备份中。

验收：按版本撤销不误伤已核定无关版本；根或客户端阻断覆盖全部依赖；撤销与认证竞争有确定顺序；旧批准、重试、重启和恢复不能把 compromised 改回可认证状态。

### 4.3 插件管理

第一版支持内置 Provider 注册，插件随主服务编译和部署。

| 类型 | 功能 |
| --- | --- |
| 内部 Provider | 内部生成、保护和使用密钥，执行认证与生命周期管理 |
| 第三方 Provider | 将统一操作适配为第三方密钥服务或认证接口调用 |
| HTTP Provider | 预留跨语言协议，后续允许其他语言独立实现，第一版不要求落地 |
| 硬件 Provider | 预留硬件密钥设备及硬件认证设备的适配接口，本期不实现设备调用 |

统一能力包括：

- 插件标识、版本和能力声明。
- 配置验证和连接检查。
- 密钥创建或引用接入。
- 密钥状态查询。
- 认证验证。
- 密钥轮换和停用。

插件只声明实际支持的能力。不支持导出、轮换或停用时，应明确返回不支持及原因，管理端不能展示为已成功执行。

第三方异常时不自动切换到不同密钥或放宽认证规则。Provider 凭据不得通过普通配置查询接口返回。

#### 硬件接入接口预留

硬件能力作为 Provider 扩展接入，不改变客户端统一认证入口。候选设备包括 HSM、TPM、安全密钥等，具体设备、厂商及协议以后确认，不要求所有硬件支持相同操作。

预留以下接口契约，实施时根据能力声明按需启用：

| 接口能力 | 预留内容 |
| --- | --- |
| 设备信息与能力查询 | Provider、设备引用、型号、协议版本及支持能力；不暴露设备凭据 |
| 连接与健康检查 | 设备是否可达、是否就绪及故障状态 |
| 密钥引用绑定与状态查询 | 使用设备内的密钥句柄或引用绑定客户端及版本，不要求导出原始密钥 |
| 设备内认证运算 | 预留 MAC 生成与校验、签名与验签等操作，由设备能力决定是否支持 |
| 硬件认证挑战 | 预留挑战生成与响应验证，后续可用于客户端或审批人硬件认证 |
| 生命周期操作 | 预留创建、轮换、停用接口，不支持时明确返回能力不支持 |

接口上下文应包含请求 ID、超时、目标密钥引用及版本；管理变更由主服务检查审批与审计后调用，设备适配器不自行决定授权。硬件挑战验证可以作为审批人的身份验证依据，但不能替代 M/N 审批计票。

统一预留设备不可用、超时、能力不支持、密钥引用无效、认证失败及执行结果待确认等结果。硬件不可用时不得自动降级到软件密钥。对于可能产生副作用的硬件操作，超时后不能直接认定失败并重复执行。

本期仅在功能设计和后续接口定义中保留上述扩展点，不接入真实设备、不集成厂商 SDK、不生成硬件密钥，也不把占位实现标记为可用。硬件密钥与现有软件密钥之间不预设可以复制或互相替代。

### 4.4 统一认证

- 对外提供统一认证接口。
- 根据 clientId、认证方式和密钥版本选择对应 Provider。
- 校验客户端状态、密钥状态和有效期。
- 返回统一认证结果及可信客户端身份。
- 业务系统根据该身份继续处理自身权限。
- 对异常认证请求限流，避免暴力尝试及第三方调用耗尽。
- 对外收敛认证失败信息，内部保留可定位原因。

候选认证方式：

| 方式 | 特点 | 当前结论 |
| --- | --- | --- |
| Bearer 共享密钥 | 实现简单，持有完整密钥即可认证 | 待确认是否采用 |
| HMAC 请求签名 | 使用共享密钥签名，需要时间戳和 nonce 防重放 | 待确认是否作为首期默认 |
| 第三方认证 | 由 Provider 调用外部能力验证 | 随目标厂商确定 |

普通认证不需要人工审批。审批用于管理变更，不进入每次请求的实时认证链路。

### 4.5 多人授权

- 配置授权人集合和通过阈值，例如 2/3。
- 发起申请时固定操作类型、目标、参数、版本、有效期及申请原因。
- 支持同意、拒绝、撤销及超时失效。
- 同一身份只能计票一次；申请人默认不能审批自己的申请。
- 提交申请后不可修改操作内容，变更后必须重新发起。
- 执行时重新检查授权条件、目标版本和当前状态，避免过期批准覆盖后续变更。
- 通过后至多执行一次；重试不得产生重复密钥或重复轮换。
- 对执行结果不明确的外部调用先查询或对账，再决定是否重试。
- 记录审批意见、执行结果及失败原因。

建议审批状态：待审批、已通过、已拒绝、已撤销、已过期；执行结果单独记录为未执行、执行中、成功、失败或结果待确认，避免将“审批通过”误认为“操作成功”。

建议操作策略如下，具体阈值和紧急权限需确认：

| 操作 | 建议策略 |
| --- | --- |
| 普通认证 | 自动处理 |
| 新建或轮换客户端密钥 | 多人审批 |
| 绑定或切换 Provider | 多人审批 |
| 修改 Provider 关键配置 | 多人审批 |
| 更换或停用基础密钥 | 多人审批 |
| 紧急停用客户端或泄露密钥 | 指定应急人员可立即执行，强制审计 |
| 重新启用客户端 | 多人审批 |
| 查询元信息 | 按管理角色授权 |

<a id="recovery"></a>
### 4.6 异常处理与恢复

区分密钥泄露和服务故障：

- 密钥泄露：识别受影响客户端和版本，紧急停用，申请新版本并完成切换。
- 第三方不可用：受控超时和重试，明确返回认证不可用，不绕过验证。
- 内部 Provider 故障：拒绝无法完成验证的请求，保留故障信息。
- 轮换失败：保留现有版本实际状态，记录新版本处理结果，支持排查和受控重试。
- 基础密钥故障：开发软件根丢失不重建同名材料，审批新根和新客户端凭据；真实 KMS/HSM 恢复及切换待实际接入，不预设万能备用密钥。

切换与停用需要明确生效时间；若未来增加缓存，应给出最大失效延迟和主动失效机制。

恢复操作先分类为“已确认未执行”“已确认成功”“结果未知”，不得根据超时或页面报错推断未执行。申请、投票、执行、交付和密钥状态各自保留，不使用一个成功/失败字段概括全部步骤。

| 异常位置 | 必须核对的权威事实 | 允许的后续动作 |
| --- | --- | --- |
| 提交申请响应丢失 | 同一身份、幂等键与完全相同参数对应的申请 | 查询或重用原键；参数变化返回冲突 |
| 本地软件预计算失败 | 是否产生已提交版本、执行记录或交付事实 | 仅在确认无外部副作用且当前批准/修订仍有效时有限重试；根预算不退款 |
| 本地执行响应丢失 | 同一申请的执行记录和目标版本 | 已成功直接返回同一结果，不重复执行；未提交事务按当前权限重新检查 |
| 领取消费后响应丢失 | claimed_at、原版本及接收方是否已取得交付包 | 不重发原秘密；停用或撤销原版本并申请新版本 |
| 持有证明确认响应丢失 | 服务器 pending/staged 状态与接收方私有凭据 | 已 staged 视为完成；仍 pending 时仅在原挑战有效且上下文一致时受控确认，不重新领取 |
| 远程签发/交付超时 | Provider operationId、权威结果查询、旧执行器隔离与目标修订 | 标为 UNKNOWN 并隔离该操作；不启动第二次签发或恢复认证 |
| 基础密钥不可用 | 不可变根身份、用途、实际材料及是否泄露 | 不降级为软件备用根；按受控方案恢复同一可信根，或用新根、新凭据重新接入 |
| 数据库/备份恢复 | 撤销事实、策略修订、审批票、已执行操作、nonce 边界和根预算高水位 | 核对完成前隔离认证与变更；不能因缺少管理员而重新 bootstrap |

- 已实现恢复任务，记录事件、客户端、新版本、证据摘要、签发申请及状态；责任人和批准通过原申请清单关联，方案变化须新建申请。恢复扩大访问权限或改变信任配置时必须独立多人审批，原请求的批准不自动覆盖恢复方案。
- 客户端已停用时，已实现的隔离恢复任务冻结环境、客户端修订、新版本、可信根、接收方公钥、证据与期限，经当前权限及独立多人审批后，才可在普通认证始终关闭的情况下准备、交付并验证新凭据。该流程仅在开发软件模式装配，不能临时启用客户端、绕过现有签发检查、重新 bootstrap 或降低审批门槛。
- 恢复上线须再经独立多人审批，在同一事务中记录受影响旧版本的停用或泄露撤销事实、激活已验证的新版本、恢复客户端、更新修订并写入审计；疑似泄露版本不提供过渡期。事务失败整体回滚，不得使旧 ACTIVE 版本随客户端恢复而重新有效。
- 远程 Provider 未实现权威结果查询、幂等或必要隔离时，不开放相应远程执行。最终一致的“暂未查到”不能作为未执行证明；旧 owner 未隔离时不接管重做。
- 进程重启不能清空执行幂等、撤销事实或预算。根预算历史无法证明完整时，不继续用同一实际根材料加密，也不能换别名把计数归零。
- 备份恢复在隔离环境验证，并与备份之外的可信撤销/审计/用量校验点比对。无法确认安全状态时保持受影响认证拒绝，重新建立可信状态；不恢复旧 Cookie、旧审批票或默认有效状态。
- 开发软件根仍只驻留进程。默认演示启动创建新域；显式 resume 入口可在独立签名状态核验及隔离后恢复原管理域，但不加载旧根，须审批新根和新密钥；它不是生产灾备方案。生产恢复依赖真实根托管、受控权限和经验证的 RTO/RPO。

验收：在提交前后、交付消费前后、确认前后和进程退出点注入故障；每次核对可得到确定状态或明确 UNKNOWN，无重复副作用、秘密重发、预算回退和撤销复活。隔离准备期间普通认证持续拒绝；最终恢复后仅符合恢复方案的新凭据可认证，失败不得恢复客户端或旧版本。不能把重启成功当作恢复验收。

### 4.7 管理身份与角色

建议支持以下职责，允许一人具备多个角色，但审批仍遵循独立身份和申请人回避规则：

- 管理员：维护客户端、Provider 配置及策略。
- 申请人：提交密钥相关变更。
- 审批人：审核授权范围内的申请。
- 审计员：只读查询操作和审批记录。
- 应急人员：按单独策略执行紧急停用。

管理人员身份来源待确认，可以接入现有身份系统；客户端共享密钥不能直接充当管理员凭据。审批人及策略本身的变更也必须受保护，不能通过临时降低阈值绕过审批。

### 4.8 审计与运行状态

- 查询客户端管理、密钥生命周期、Provider 变更、策略变更、审批及执行记录。
- 记录操作人、时间、请求 ID、目标、目标版本、处理结果和原因。
- 认证日志按风险和频率控制记录，不在高频路径重复刷屏。
- 不记录密钥明文、token、Provider 凭据和其他敏感请求内容。
- 提供服务健康检查、Provider 可用性和异常统计。
- 审计记录不提供普通管理接口修改或删除；留存周期和外部归档方式待确认。

已实现范围查询/页面、条件固化 JSONL 快照、下载再鉴权、认证成功同事务留痕、固定原因失败聚合，以及 outbox、独立 Ed25519 文件归档和外部清单校验。作用域及归档覆盖从迁移 7 启用后开始，旧记录保留但不猜测范围回填。以下为设计规则，实际字段、固定开发限制与未接入部分以[运行手册](生命周期运行手册.md#audit)为准：

| 能力 | 规则及产品判断 |
| --- | --- |
| 关联追踪 | 以环境、客户端/密钥版本、申请、执行、轮换/恢复事件和服务端 request ID 串联；批准、执行、交付、认证分别记录 |
| 事件内容 | 服务端事件 ID、数据库记录时间、操作者/服务身份、范围、操作、前后修订、结果、原因码和证据引用；不把记录时间冒充精确提交时刻 |
| 查询 | auditor 只读角色加当前环境/客户端范围；按时间、对象、操作、结果、事件关联筛选并限制页大小；失去授权后不能继续读取旧查询结果 |
| 导出 | 默认版本化 JSONL，受控 CSV 可选；使用一致性快照或物化任务记录筛选范围与条数，下载前复查权限并审计导出行为，文件短期私有访问 |
| 文本安全 | 明文密钥、Token、Cookie、签名/MAC、Provider 凭据和交付包不导出；参数采用字段白名单。CSV 对不可信文本做公式注入防护，不能仅依赖引号包裹 |
| 可靠归档 | 关键变更与本地审计/outbox 同事务，异步归档按事件 ID 去重，展示积压/失败；不把 outbox 或归档占位当成已实现 |
| 篡改检测 | 只追加、更正另记关联事件；独立权限域归档并保留可信校验点，不能仅靠同库哈希链或导出文件摘要声称抵御数据库管理员篡改 |
| 认证拒绝 | 使用受限原因码、聚合、限流与保留策略；未验签的 clientId 仅为声明值，不认定为真实操作者，不制造无限基数标签或逐请求刷库 |

大批量导出需有任务状态、范围、有效期、失败原因及结果摘要；不能以跨页的普通实时查询冒充一致性快照。留存周期、归档存储、告警接收方和导出上限仍需环境确认，未配置时不宣称归档验收通过。外部通知只预留集成，配置资料本身不授权发送消息。

验收：越范围查询/导出拒绝、撤权后的分页和下载拒绝、审计写入失败回滚敏感变更、归档重试不重复事件、字段脱敏、CSV 文本安全、快照一致性，以及删除/篡改/缺段可检测。审计异常不能把认证拒绝改为通过。

<a id="flows"></a>
## 5. 典型流程

### 5.1 客户端接入

创建客户端 → 选择 Provider 和认证方式 → 发起密钥申请 → 多人批准 → 创建或绑定密钥 → 受控交付 → 客户端认证。

### 5.2 正常认证

接收认证请求 → 检查客户端及版本状态 → 调用 Provider → 执行必要的防重放校验 → 返回认证结果与客户端身份。

### 5.3 密钥轮换

提交轮换申请 → 多人批准 → 创建新版本 → 客户端切换 → 过渡期结束 → 旧版本失效 → 记录结果。

### 5.4 泄露处置

发现泄露 → 应急停用受影响客户端或版本 → 记录原因及影响 → 审批隔离恢复方案 → 保持普通认证关闭并准备、交付、验证新版本 → 独立审批 → 原子撤销受影响旧版本、激活新版本并恢复客户端。此为已实现的开发隔离恢复流程，见 4.6。

## 6. 工程组织建议

```text
ex-keygate/
├── cmd/keygate/             服务入口
├── internal/
│   ├── client/              客户端管理
│   ├── key/                 密钥生命周期
│   ├── auth/                认证流程
│   ├── approval/            多人授权
│   ├── audit/               审计
│   └── provider/            Provider 调度
├── providers/
│   ├── local/               内部实现
│   ├── thirdparty/          第三方适配
│   └── hardware/            硬件适配预留，本期不实现
├── api/                     HTTP 接口规范
├── protocol/                跨语言插件协议
├── web/                     管理页面
└── docs/                    设计与使用文档
```

建议使用一个 Go module，最终交付一个可执行文件，可在多个节点部署相同程序。Go module 的正式路径在确定仓库地址后设置。管理页面可以内嵌。数据库选型、密钥保护方案和部署方式在技术设计阶段确定。

### 6.1 多节点与多数据中心

多节点用于承受单进程或单机器故障，多数据中心用于降低单个机房或地域故障的影响。它们提升可用性和容灾能力，但不会自动提升密钥保密性；更多副本也会扩大密钥接触面，必须控制副本范围和权限。

推荐分阶段实施：

| 阶段 | 运行方式 | 范围 |
| --- | --- | --- |
| 首期生产基线 | 同地域跨故障域部署多个应用节点 | 无状态接入，共享具备一致性保证的持久化与防重放设施；消除应用单点 |
| 跨地域灾备 | 主地域提供服务，备用地域受控接管 | 复制数据、独立备份、恢复演练和明确切换流程 |
| 多中心运行 | 按需求支持多个中心认证接入 | 需要解决跨中心一致性、延迟及密钥驻留，单独评审后实施 |

具体节点数、故障域和仲裁成员分布在部署设计时确定，应用节点数量不等于数据库仲裁节点数量。两个数据中心不能仅凭互相探测就保证安全自动切换；需要可靠的仲裁与旧主隔离，必要时引入独立故障域的仲裁能力，不预设任意一中心失效后均可自动继续写入。

### 6.2 状态一致性与并发规则

- 客户端状态、密钥版本、停用记录、审批策略、审批票和执行记录属于安全关键状态，必须由权威存储提供事务和所需的一致性保证。
- 同一操作通过唯一操作 ID、版本校验及原子状态流转控制执行；节点切换后仍不能重复生成或启用密钥。第三方副作用还需 Provider 幂等或结果核对，不能仅靠本地事务宣称全链路恰好一次。
- 密钥和审批变更采用单一权威写入路径或具备等效一致性保证的存储，禁止各中心独立批准后再异步合并票数。
- 同一密钥可在多个节点认证时，nonce 去重必须覆盖所有允许认证的节点和中心。可以使用共享一致性判定，或将密钥分配到唯一权威认证区域；禁止每个中心独立去重却宣称全局防重放。
- 严格安全模式下，节点必须确认读取到当前有效状态后才允许认证；无法确认停用、版本或权限状态时拒绝请求。异步只读副本及未验证新鲜度的本地缓存不能承担最终授权判断。
- 网络分区时，无法访问权威状态或取得所需仲裁的一侧停止相关认证和敏感变更，不以可用性为由放宽校验。若未来允许有限离线认证，必须单独批准其撤销延迟和风险，不能默认启用。

### 6.3 故障切换与密钥保护

- 接管前隔离旧主的写入及密钥操作权限，防止网络恢复后双主执行；流量切换不等于权限隔离完成。
- 切换后校验审批、版本、停用与执行记录；若状态可能回退，应暂停受影响认证并完成核对，不直接开放备用中心。
- HMAC 认证需要相应运算能力可用；各中心能否持有同一密钥、使用区域独立密钥，或调用远程硬件，需结合驻留政策及设备能力决定，不默认可以复制不可导出密钥。
- 备份、复制链路、节点间通信及远程 Provider 均需加密和双向身份认证，数据中心间采用独立、最小权限身份。
- 服务入口、权威存储、防重放设施、Provider 和审计链路均需评估单点，不能仅部署多台应用服务器便宣称整体高可用。

### 6.4 容灾验收

- 分别定义认证、管理变更、审计的 RTO（恢复时间目标）和 RPO（可接受数据丢失目标），具体数值待容量和成本评估。
- 已确认的安全关键变更原则上要求切换后不丢失；若异步灾备不能保证，应停止相关服务并核对状态，不能使用旧状态继续授权。
- 验证节点宕机、存储故障、中心断网、网络分区、旧主恢复、切换中轮换、跨节点重放、重复审批及备份回滚。
- 验收需证明停用不会因切换而失效、审批不会重复计票、操作不会被无控制地重复执行，并记录实际恢复时间及数据恢复点。

## 8. 安全要求与发布门禁

以下为本项目设计要求，具体算法与协议参数在技术设计时评审确定，优先使用成熟标准和经过维护的实现，不自行设计密码算法或私有加密协议。

### 8.1 密钥与客户端隔离

- 不同客户端、环境和用途分别使用密钥，禁止将全局基础密钥作为客户端共享密钥下发。
- 密钥使用密码学安全随机源生成；禁止默认密钥、硬编码密钥及将明文密钥写入仓库、日志或备份。
- 仅需验证的高熵 Bearer 凭据可保存摘要；需要执行 HMAC 的密钥必须可供运算，不能误用摘要代替，应以认证加密保护并隔离密钥加密密钥。
- 基础密钥与受保护数据分离保存；硬件模式优先使用不可导出的设备内密钥，只传引用和运算结果。
- 明文交付必须绑定目标身份、短期有效且只能受控领取，禁止通过邮件、普通日志或长期可访问链接传递；恢复流程不得提供绕过授权的明文导出后门。
- 关闭敏感请求体记录及非必要内存转储，限制进程权限和密钥驻留时间；Go 托管内存下不承诺绝对零化。
- 浏览器或其他不受控终端不能把静态共享密钥视为可靠秘密；此类客户端需另行选择硬件密钥、非对称认证或受信任服务端代理方案。

### 8.2 通信、认证与防重放

- 所有认证和管理通信使用经过验证的加密传输；服务间及远程 Provider 使用双向身份认证，禁止关闭证书校验。
- 高安全场景优先选择请求签名或受保护的非对称认证；Bearer 方案仅在明确适用边界后启用，不作为无条件通用默认。
- 请求签名必须绑定身份、版本、方法、目标路径及查询参数、正文摘要、时间戳和 nonce，规定一致的规范化规则。
- 防重放判定需在并发及多实例环境下原子生效；防重放存储异常时拒绝依赖该能力的认证。
- 认证结果不得信任调用方自行填写的身份字段；跨服务传递结果必须绑定受众、用途及短有效期，或在可信通道内直接使用。
- 明确请求大小、超时、并发、限流和重试上限；错误响应不泄露密钥是否存在及内部设备详情。

### 8.3 管理与多人授权

- 管理人员使用独立实名身份和多因素认证，高敏感操作要求再次认证；禁止共享审批账号。
- 密钥使用、密钥管理、策略维护和审计职责分离，采用最小权限及默认拒绝。
- 修改审批人、阈值、应急权限、Provider 信任配置及恢复策略同样需要多人审批，不能自批或通过降低阈值绕过控制。
- 审批绑定不可变操作摘要、目标版本及期限；执行时原子检查审批、状态和执行次数。
- 初始信任建立必须有独立受控流程，完成后关闭引导入口；账号找回、管理员重置和灾备恢复不能绕过多人授权。
- 应急权限只能缩小权限或停用认证，不能导出密钥、恢复访问或放宽校验；应急操作需要告警和事后复核。

### 8.4 插件信任与执行隔离

- 插件视为受信任计算边界的一部分，只允许经过审查、固定版本的插件进入发布产物。
- Go 进程内插件不具备内存隔离；要求抵御插件失陷时，应采用独立进程和受限凭据，不能以单进程部署替代必要隔离。
- 远程插件地址由受控配置决定，禁止请求方指定任意地址；限制网络出口，防止 SSRF 及凭据发送到非授权目标。
- 每个 Provider 使用独立、最小权限凭据；设备不可用或能力不支持时拒绝操作，不降级到弱认证或备用万能密钥。

### 8.5 审计、备份与安全验收

- 关键管理操作及其审计意图需可靠保存后才能执行；无法可靠留痕时拒绝敏感变更。
- 审计向独立权限域归档，并具备篡改检测；仅数据库只读接口不足以抵御数据库管理员篡改。
- 备份加密、访问隔离、按期验证恢复；恢复后保持停用状态、防重放边界及审批约束，防止旧备份复活已撤销凭据。
- 发布前完成独立安全审查、依赖和秘密扫描，以及认证绕过、重放、并发审批、越权、故障降级和恢复测试。
- 生产部署前明确漏洞处置、密钥泄露应急流程、停用生效上限和安全告警；未验证控制和剩余风险逐项记录，不以功能完成代替安全验收。

参考依据：以上为项目安全策略，参考 [OWASP Key Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html) 和 [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) 中的密钥生命周期、隔离存储和最小权限原则；不代表已满足某项认证。

<a id="decisions"></a>
## 9. 待确认事项

1. 多人授权是否采用 M/N 审批，还是确实需要多人持有密钥分片。
2. “基础密钥”的准确业务用途，以及客户端共享密钥出问题后的预期恢复方式。
3. 客户端类型：服务端应用、桌面程序、移动端或浏览器。客户端环境影响共享密钥可保护程度和认证方式选择。
4. 首期采用 Bearer 还是 HMAC，以及认证结果如何被业务服务使用。
5. 第一个第三方密钥服务或认证厂商。
6. 管理员与审批人的身份来源、审批阈值及应急权限。
7. 密钥首次交付、基础密钥保护、备份和恢复方式。
8. 数据存储、部署环境、审计留存及可用性要求。
9. 后续硬件类型、部署位置、厂商协议及用途：保护基础密钥、客户端认证或审批人身份验证；本期不依赖此项确定即可继续设计。
10. 数据中心数量、地域及网络条件，认证与管理链路的 RTO/RPO、跨中心延迟预算、数据驻留限制和部署成本；是否首期落地跨地域灾备。
