# 持久启动与受控升级

本流程用于当前开发／测试软件模式，管理人员和业务状态保存在原 PostgreSQL 权威库，根材料经独立包装密钥加密后保存。生产环境继续受 KMS/HSM 与基础设施验收门禁限制。

## 与临时演示的区别

| 模式 | 管理域 | 根材料 | 重启行为 |
| --- | --- | --- | --- |
| 原 `keygate-dev -enable-key-flow` | 每次创建新域 | 仅在内存 | 不支持原域无损重启 |
| `-runtime-action init` | 在专用空库首次创建 | 加密保存，包装密钥在部署目录外 | 只初始化，不开放 HTTP |
| `-runtime-action run` | 读取原域 | 解封原登录保护根和全部已启用客户端根 | 不重做初始化、不导入初始账号或 MFA |
| `-runtime-action plan` | 读取原域 | 不修改业务根 | 生成当前候选发布计划，不激活 |
| `-runtime-action upgrade` | 保留原域 | 保留原根 | 校验外部签名检查点、停服及发布代次后激活 |

既有临时进程没有事先保存根材料，不能事后从数据库密文推导根。不要停止旧演示并声称能够直接迁移；需要另行设计有原材料的受控迁移或隔离换钥。现有隔离恢复命令也不等于正常重启。

一个持久部署使用专用数据库，不能把已经包含其他演示域的库接管为新部署。首次初始化有数据库会话锁和不可覆盖的目录／安全域哨兵，失败时不会自动重开初始化。

## 初始化准备

1. 创建专用、可持久保留的 PostgreSQL 开发数据库。当前 CLI 仅接受回环地址、库名 `keygate_dev`；数据库应使用命名持久卷及独立备份，不使用自动删除的临时容器。`start-dev-db.py` 提供一次性测试库，不适合承载持久管理域。部署目录与签名检查点不包含数据库行数据，不能在数据库丢失后代替备份恢复。
2. 准备可信 localhost TLS、固定地址的模拟 SSO、初始 MFA 与账号计划。此入口目前只初始化模拟身份，不能视为真实企业身份系统初始化。
3. 从受保护通道提供独立随机32字节包装密钥文件，权限0600，保存在部署目录之外。不要通过命令行、聊天或 Git 传递密钥值。生产前替换为经过验收的托管能力。
4. 使用 `keygate-ops -action init-signing` 创建检查点签名身份，独立保管私钥；初始化时固定其公钥。以后不能在升级时临时换一把公钥认可自己生成的检查点。
5. 固定构建产物。实际可执行文件的 SHA-256 纳入修订；不同构建不能借普通启动绕过升级。

以下路径均为示例，应指向本机已准备的私有文件；不包含任何真实密码或密钥值。

```sh
go build -o ./bin/keygate-dev ./cmd/keygate-dev
go build -o ./bin/keygate-ops ./cmd/keygate-ops

./bin/keygate-ops -action init-signing \
  -signing-key /secure/operator/checkpoint.key \
  -public-key /secure/operator/checkpoint.pub

KEYGATE_ENV=development KEYGATE_ROOT_MODE=development_software \
./bin/keygate-dev \
  -runtime-action init \
  -runtime-dir /secure/keygate/deployment \
  -runtime-key-file /secure/separate/wrapping.key \
  -runtime-public-key /secure/operator/checkpoint.pub \
  -port 18931 \
  -database-file /secure/keygate/database-url \
  -sso-file /secure/keygate/sso/connection.json \
  -tls-dir /secure/keygate/tls \
  -mfa-config-file /secure/bootstrap/mfa.json \
  -local-accounts-file /secure/bootstrap/accounts.json \
  -output /secure/keygate/console
```

部署目录必须事先不存在，其父目录已存在。包装密钥不能实际位于部署目录内，父目录符号链接也不能绕过此规则。初始化完成日志给出 `environment` 和 `deployment_id`，保留这些非敏感标识。

## 普通启动与停止

```sh
KEYGATE_ENV=development KEYGATE_ROOT_MODE=development_software \
./bin/keygate-dev \
  -runtime-action run \
  -runtime-dir /secure/keygate/deployment \
  -runtime-key-file /secure/separate/wrapping.key \
  -runtime-node node-a
```

普通运行参数从数据库选定的加密修订中读取。不能再通过 `-port`、`-sso-file`、`-mfa-config-file` 等参数覆盖；在线更新后的账号、权限和 MFA 也不会被初始计划覆盖。

启动会检查数据库迁移账本、协议版本、二进制摘要、配置依赖、原身份配置、根指纹及当前节点租约。任何缺失、篡改、错根、未知未来版本或配置漂移都拒绝启动，不生成替代根。配置由同一份校验字节构建私有快照后装配，避免先校验、后重读不同文件。

发送 SIGTERM 进行优雅停止。节点摘流后再启动会增加 incarnation，不改变管理域。进程被强杀或启动中失败时，旧租约最多保留15秒；等待其过期，不强抢租约。同一个 node ID 不能同时运行两个实例。不同节点使用唯一 ID，并从受保护的同一部署材料／已核验副本加载配置；跨主机共享部署仍需外部受控分发和真实部署验收。

`/health/live` 仅说明进程存活；`/health/ready` 核验数据库、租约与根。缺少新批准根的节点拒绝就绪和相关认证，须重新加载受保护材料，不能使用“健康缓存”放行。

## 根与配置的持久化规则

部署目录中的 `index.sealed` 保存加密的登录保护根、管理域定位及固定升级公钥；每个修订和客户端根分别加密保存。数据库保存当前修订号与摘要、原身份摘要以及根指纹，运行时以数据库为准，不凭目录中“最新文件”猜测。

审批新根时，先完整加密落盘并同步文件和目录，再提交数据库登记。数据库提交失败可留下孤立密文；重试会复用它，但没有数据库审批事实的文件不能获得认证资格。真实 I/O 或同步失败拒绝继续，不能以“还能读到文件”代替持久性确认。

初始账号密码摘要与 MFA 计划仅用于首次离线引导，不作为每次启动的配置源。保存的日常设置只有配置文件引用与受保护的依赖摘要，不把数据库密码、TOTP 种子或软件根明文写入 Git、日志和公开连接元数据。

运行中的 `.snapshot-*` 为0700私有临时装配目录，可能包含原配置已引用的 TLS／状态签名材料副本，正常退出清理。备份不要收集运行快照；崩溃遗留仅在确认对应进程不再使用后由操作者清理。软件根始终以密文保存，包装密钥不得与部署备份一起打包。

## 受控发布升级

当前实现支持 **protocol 1、schema 23 内的二进制和兼容配置升级，以及明确的 schema 21/22→23 升级**。普通启动只接受23且不执行DDL；plan/upgrade可校验21、22的完整迁移账本，先核对旧安全检查点，再在同一事务内迁移DDL、发布修订和推进代次。失败整体回滚。其他跨schema迁移、未知未来协议及身份体系切换仍拒绝，不能声称已有通用跨版本迁移器。

```text
固定新构建 -> 生成计划 -> 独立审查
                         |
                         v
                 所有节点停止／摘流
                         |
                         v
             核验权威库与外部签名检查点
                         |
                         v
            候选加密修订落盘 -> 原子激活
                         |
                         v
               旧配置隔离 -> 新版run
```

1. 保留旧构建、当前部署备份和目录外包装密钥，分别保管。准备新构建，不直接替换仍运行的可执行文件路径。
2. 用新构建执行 `-runtime-action plan`，核对部署 ID、原／目标修订、配置摘要、schema 和 protocol。计划不批准操作，仍需组织自己的变更审查。
3. 如需改兼容配置，使用 `-runtime-next-config /secure/candidate.json` 提供完整 `deployment.Settings` 对象，包含 port、databaseFile、ssoFile、ssoSecretFile、tlsDirectory、pluginFile、mfaPluginsFile、trustDirectory、reminderFile、output，未使用的可选项为空字符串。路径转为绝对路径。不能隐式切换数据库或登录身份配置；MFA 插件信任变化引起身份摘要变化时也拒绝。
4. 停止所有应用节点，确认摘流或租约过期。用初始化固定公钥对应的独立签名身份，通过 `keygate-ops -action capture-state` 在权威库生成最新签名检查点。数据库连接使用该工具原有的私有环境配置，不把 DSN 拼进命令或文档。
5. 用新构建执行 `upgrade`，传入检查点。CLI 复核签名、公钥、管理域、最新状态、原修订、无活动租约及身份摘要；事务激活修订并推进集群代次。
6. 用同一新构建执行 `run`，检查 ready、原人员／策略、旧凭据按原有效期验证、密钥认证与审计。旧构建或旧配置普通启动会拒绝。

```sh
KEYGATE_ENV=development KEYGATE_ROOT_MODE=development_software \
./bin/keygate-dev-next -runtime-action plan \
  -runtime-dir /secure/keygate/deployment \
  -runtime-key-file /secure/separate/wrapping.key

# 停服、独立审查及检查点签名完成后激活。
KEYGATE_ENV=development KEYGATE_ROOT_MODE=development_software \
./bin/keygate-dev-next -runtime-action upgrade \
  -runtime-dir /secure/keygate/deployment \
  -runtime-key-file /secure/separate/wrapping.key \
  -runtime-checkpoint /secure/operator/latest-state.signed
```

候选修订文件名同时包含修订和摘要，失败的其他候选不会覆盖或锁死下一次受控候选。激活提交结果不明时，先读取数据库实际当前修订再处理；不凭进程错误回写旧状态，也不删除撤销、防重放、预算或审批记录。

## 回退、备份与恢复

同 schema 的旧构建如需重新发布，也必须作为新的受控修订，经最新检查点和变更审查推进代次。不能把数据库与目录复制成“以前的样子”绕过撤销和审计。版本不兼容时拒绝回退。

正常重启假设权威数据库未回滚，不能证明灾备副本新鲜度。数据库恢复、主库切换和包装密钥丢失分别按独立检查点、旧主隔离、备份隔离及组织密钥恢复流程处理。不要通过 `init` 找回已有域；不要删除初始化哨兵。包装密钥的轮换及21/22→23以外的跨schema迁移仍需后续方案。

【涉及其他业务】共享的登录保护、MFA 密文、客户端根、审批执行、节点租约和安全检查点均受此生命周期约束；原临时演示命令保留原行为。生产托管、真实多中心与灾备验收仍未完成。

## 本次开发验收

2026-10-20，15项开发安全验收全部通过，包含静态检查、SDK、已知漏洞检查及独立 PostgreSQL 下 race／故障回归；另覆盖加密文件篡改、错误包装密钥、父目录别名、装配快照一致性和目录同步失败。

专用演示实际完成首次初始化、普通停止／重启、两次受控二进制升级。正常重启对比48个安全状态表，仅节点租约发生预期变化；原人员、账号、MFA、审批、新批准的根与预算保留。升级后使用原密码和 TOTP 验证成功，旧 MFA 到期后仍要求重新验证。新构建直接运行、活动节点升级与升级后旧构建运行均拒绝。上述结果仅代表本机开发演练。
