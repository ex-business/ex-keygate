# 阶段 1.3：权限与多人授权

日期：2026-10-19。状态：v1 权限设计，尚未开放对应管理操作。现有会话仅确认身份，现有审批领域对象还不具备本文全部权限校验。

## 1. 模型

采用角色 + 资源范围，默认拒绝；不引入通用规则引擎。范围为环境及指定客户端集合，跨范围不得查询或变更。SSO 的 issuer/sub 确认身份，本地授权表决定操作权限；不直接把 email、昵称、测试账号名或任意 SSO roles 当作管理权限。

必须区分：申请权限、审批权限、执行权限、读取审计权限和应急停用权限。业务系统自身的业务权限不迁入 ExKeyGate。

| 角色 | 可以做 | 不允许直接做 |
| --- | --- | --- |
| viewer | 查看范围内客户端、密钥元信息和自身申请 | 读取明文、修改资源 |
| requester | 发起范围内客户端/密钥变更申请 | 自批、直接执行获批前变更 |
| approver | 对范围内允许类型的申请投票 | 修改申请内容、重复计票、审批自己的申请 |
| policy_admin | 发起身份、角色、策略、Provider 配置变更 | 不经审批直接授予权限或降低阈值 |
| auditor | 读取范围内审计 | 修改/删除审计、管理密钥 |
| emergency_operator | 立即停用、撤销或收紧权限 | 导出、激活、恢复、降低校验强度 |
| executor_service | 消费具体获批操作并执行其清单 | 发起/审批自己的授权、接收任意外部参数执行 |

同一人可以具备多角色，但申请人回避和自然人去重不能被角色叠加绕过。policy_admin 不是万能超级账号，executor_service 不是给前端发放的角色。

## 2. 操作矩阵

| 操作 | 发起 | 批准 | 执行 |
| --- | --- | --- | --- |
| 创建/启用客户端、修改认证 Profile | requester，涉及信任配置时 policy_admin | 范围内独立 approver，至少 2 人 | 内部执行器 |
| 签发/激活/轮换/正常停用密钥 | requester | 范围内独立 approver，至少 2 人 | 内部执行器 |
| KEK 变更、Provider 信任配置、接收方指纹变更 | policy_admin | 对应高敏感操作审批池 | 受限执行器/受控发布流程 |
| 人员绑定、角色授予、策略成员/阈值变更 | policy_admin | 现行受信策略的独立审批池 | 内部执行器，不以新策略批准自己 |
| 应急停用客户端/版本/人员授权 | emergency_operator | 可立即执行 | 缩小权限的专用处理器，强制审计与告警 |
| 恢复客户端、重新授权 | requester 或 policy_admin | 至少 2 人 | 内部执行器；已泄露密钥版本不恢复 |
| 只读元信息/审计 | viewer / auditor | 不需逐次审批 | 每次读取校验当前范围 |
| 领取初始客户端密钥 | 被批准的接收方 | 沿用绑定该接收方的签发批准 | 交付处理器，不允许管理员代领 |

v1 默认 M=2；N 为操作发起时有效且匹配范围的独立审批人员数，N 必须 >=2。生产建议配至少 3 名合格审批人用于轮休，但人数配置仍应经实际组织确认；当前 3 个模拟账号不能证明有 3 个独立自然人。

## 3. 一次审批的固定内容

申请提交时固定：环境、操作类型、目标、目标修订、非敏感参数、接收方指纹、预期影响、策略 ID/版本、有效审批池、人数阈值和截止时间。变更任意内容必须新建申请；前端不能在批准后另传执行参数。

新增操作清单采用严格版本化 schema，拒绝未知及重复 JSON 字段；业务整数不得超出跨语言安全整数范围，大版本号按十进制字符串编码。摘要采用 SHA-256 与 [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785.html) 的确定性表示，集合型数组按稳定 ID 排序，有序业务数组保留 schema 规定的顺序；时间统一为 RFC 3339 UTC 格式，固定三位毫秒并使用 Z 后缀。

现有 `approval.Request.Digest()` 是 Go 内部快照摘要，不是 JCS 跨语言协议。阶段 2 必须增加 digest/schema 版本，旧开发申请显式失效并重建；不能重算摘要后继承旧票。运维页面必须展示与投票摘要完全一致的操作内容。

## 4. 资格、计票与撤权

1. 从权威库读取启用人员及当前角色，检查范围、操作类型与近期强认证要求。
2. 从审批池排除申请人以及映射到同一 personId 的其他账号；不足阈值拒绝发起。
3. 每个人每个申请最多一票。数据库同时约束 principalId 与 personId，不能只按不同 OIDC sub 算不同人。
4. 账号与自然人映射来自受控身份治理及多人核验，不能由账号自行声明，也不能仅凭 email 推断。系统无法单靠密码学判断两个账户背后是否同一个人。
5. 投票时核对摘要与资格；任意拒绝结束本次申请。过期、撤销、已执行或内容冲突时拒绝继续投票。
6. 执行前重新检查当前人员状态、自然人映射修订、范围、策略版本、目标版本和每张有效批准票。失去资格的票不能继续支撑执行，不自动补票或替换审批人，重新发起申请。

敏感写操作及审批暂定要求最近 5 分钟内的实际强认证。会话不能用刷新 Cookie 延长 auth_time；生产真实 ACR 与再认证流程未配置时，高敏感操作保持禁用，模拟 ACR 仅用于开发闭环测试。

## 5. 并发与执行

权限变更与操作执行使用一致的事务/锁顺序。只有在同一权威事务中完成最终资格检查、占用执行记录、修订更新和审计后，才能进行获批副作用。每个 requestId 只有一个 executionId；同一个执行器重试不能重复签发或重新扩大权限。

远程 Provider 调用不放在数据库长事务里。先提交操作占用，再按固定 operationId 调用幂等能力，随后按占用时目标 revision 与 owner_epoch 做 CAS 写回，并重新检查停用、撤权等阻断条件。占用后发生应急停用时，晚到成功响应不得把 DISABLED 恢复为 ACTIVE；远端已发生的副作用记录为隔离/待核对结果。结果不明确进入 UNKNOWN 并核对，不盲目重复调用；批准成功、执行成功和交付成功分别记录。

## 6. 初始化及应急

- 初始受信人员与策略通过一次性受控 CLI/部署流程核验配置清单，至少两名独立负责人在系统外确认并留存证据。
- 初始化只允许空安全域，原子写入人员/范围/阈值与审计后关闭；不能把“当前没有管理员”当作可重新初始化的条件。
- 无永久超级密码、通用恢复 Token 或 HTTP 调试授权开关；生产不得接受模拟身份源。
- 应急只能收紧状态。审批人不足时不降低阈值，恢复走独立受控灾备流程；此流程尚未实现，不能用人工直接改库视为完成授权。
- 任意数据库/服务器全权管理员仍可能绕过软件规则；若要求抵御其恶意操作，需硬件或独立执行授权边界，业务审批本身不构成密码学门限控制。

## 7. 实施差距与验收

新增本地人员、personId 绑定、范围授权、策略版本、投票资格及执行事务。现有审批对象目前仅按账号去重，阶段 2 必须补自然人和当前权限约束；现有开发登录不得自动给任何账号授予角色。

必须覆盖：越范围读取、自批、同人多账号、人员撤权、策略替换、旧票继续执行、目标并发修改、重复执行、初始化重开、应急恢复越权。当前未完成这些验证。

影响范围：本次只写设计，不授予真实人员权限，不修改 SSO 配置、其他业务权限或 base 模块。
