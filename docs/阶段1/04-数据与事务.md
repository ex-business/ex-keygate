# 阶段 1.4：数据与事务设计

日期：2026-10-19。状态：逻辑模型与事务决策，尚未执行 DDL。不是最终 SQL 迁移文件，不应直接据此修改真实数据库。

## 1. 存储边界

PostgreSQL 为安全关键状态的权威写入源，采用现有 `keygate` schema。v1 每个部署安全域使用独立受控数据库；模型显式携带 environment，所有关联均包含环境，避免仅按全局 clientId 联表。暂不引入多租户平台或独立 Redis 授权缓存。

所有时间使用 timestamptz，关键判定使用数据库时间；所有状态变更增加 revision。标识统一为受限长度文本，外部 JSON 大整数版本使用十进制字符串，避免不同语言精度损失。凭据材料不进入 JSON 参数、审计或列表响应。

## 2. 目标逻辑表

| 表/集合 | 关键字段及约束 | 业务用途 |
| --- | --- | --- |
| principals | environment、principal_id、issuer、subject_hash、person_id、person_binding_revision、enabled、revision | 绑定可信外部身份及自然人；唯一环境/issuer/subject_hash |
| role_grants | environment、principal_id、role、scope_type、scope_id、enabled、revision | 当前角色与范围，唯一同一授权；外键指向当前人员 |
| auth_profiles | environment、profile_id、version、client_type、method、provider_id、parameters_digest、state | 不可变认证配置版本；变更另建版本 |
| clients | environment、client_id、name、type、profile_id/profile_version、state、revision | 唯一环境/clientId，Profile 类型必须匹配 |
| providers | environment、provider_id、version、kind、capabilities、config_ref、trust_revision、state | 仅存受控配置引用，不存明文 Provider 凭据或请求方 URL |
| root_keys | environment、root_id、provider_ref、purpose、state、revision | 不可变 KEK 引用与用途；实际秘密在 KMS/HSM 或开发进程内 |
| root_budgets | root_id、used、maximum | 现有原子预算；root_id 全局唯一绑定实际 KEK，不因环境别名重复注册 |
| client_keys | environment、key_id、client_id、purpose、revision | 逻辑密钥身份；同环境客户端的认证用途唯一 |
| key_versions | environment、key_id、version、state、not_before、not_after、cipher_or_ref、root_id、wrap_revision、delivery_state | 唯一环境/keyId/version；密文与外部引用二选一，不保存明文 |
| delivery_claims | environment、claim_id、key_id/version、recipient_fingerprint、nonce_hash、expires_at、consumed_at | 受控单次领取及持有证明，不能作为普通认证 |
| approval_policies | environment、policy_id、version、threshold、eligible_members、scope、state | 不可变策略版本，显式保存成员/范围快照 |
| approval_requests | request_id、environment、manifest_schema、digest_version、manifest、digest、applicant、policy_ref、expires、decision、revision | 内容与摘要固定；扩展当前开发快照模型 |
| approval_votes | request_id、principal_id、person_id、person_binding_revision、decision、voted_at、auth_evidence_ref | 唯一 request/principal，且唯一 request/person；不存原始 Token |
| operation_executions | execution_id、request_id、manifest_digest、state、owner_epoch、provider_operation_id、result_ref、revision | request_id 唯一；明确 UNKNOWN 状态及占用 fencing |
| idempotency_records | environment、actor_id、operation_kind、idempotency_key、parameters_digest、request_id/result_ref | 相同键不同参数返回冲突，不能替代 nonce |
| audit_events / audit_outbox | event_id、request_id、actor、resource、action、before/after_revision、result、reason、sequence | 与状态同事务写入；outbox 支持可靠独立归档 |
| login_states / sessions | 原有 state/browser/profile 摘要、加密 verifier、会话摘要、认证时间、期限、撤销 | 沿用已实现登录隔离，不把会话当角色缓存 |
| replay_nonces | 原有 scope_hash、nonce_hash、expires_at | 唯一作用域/nonce；原子消费且保留完整接受期 |

上表是逻辑实体，身份成员与范围等多值字段应按查询、锁和约束需求规范化为关联表，不为了表少而把所有权威权限藏进不可约束的 JSON。root_id 对应的环境/用途必须与目标键一致，由事务与受约束引用同时检查。

## 3. 关联约束

- 客户端、Profile、Provider、密钥及版本均建立带环境的引用，不允许跨环境外键拼接。
- 已撤销、曾被使用及审计引用的记录不级联删除；v1 管理 API 不做硬删除。
- 同一逻辑密钥最多一个 ACTIVE 新版本，可同时有一个 RETIRING 旧版本；用唯一条件索引和事务限制，不能只在页面检查。
- 状态列采用明确允许值及转换规则。notAfter 必须晚于 notBefore；过期按时间判断，后台状态清理只是展示维护。
- 不可变 Profile/策略版本只能停用，不能原地改内容；数据库权限及应用更新路径共同限制。
- 审批元信息和投票不能随意覆盖，执行记录不因申请列表删除而消失。审计应用角色不能 UPDATE/DELETE，但数据库超级用户仍是更高信任边界。

## 4. 原子边界

| 操作 | 必须在同一数据库事务里完成 |
| --- | --- |
| 发起申请 | 当前权限/策略/目标检查，冻结清单与资格快照，幂等登记，创建审计 |
| 投票 | 按统一锁顺序锁策略、人员、目标及申请，检查当前人员/范围/绑定修订，验证摘要，写唯一票，更新批准状态及审计 |
| 占用执行 | 锁权限与策略、申请和目标，重新核票，CAS 目标修订，唯一执行记录与审计/outbox |
| 提交本地密钥结果 | 检查同一执行占用/epoch，CAS 占用时目标修订并复查停用/撤权，保存密文和状态，推进执行修订，审计/outbox |
| 激活或轮换 | 锁客户端及逻辑密钥，检查目标/策略/交付条件，更新新旧版本及期限，审计 |
| 停用/应急撤销 | 锁目标，单调收紧状态、增加 revision、记录审计；不等待后台消息或本地缓存失效 |
| 正常请求认证 | 最终检查客户端/Profile/Provider/根/版本状态与期限，原子消费 nonce，提交后才返回成功 |
| 身份/角色/策略变更 | 当前受信规则检查、版本切换、撤权状态及审计；不由新策略授权本次变更 |

签名运算可在事务外读取密文/引用后执行；提交认证结果前须在事务中重新检查所有依赖修订，变动即拒绝或受限重算，不能拿旧结果放行。回放 nonce 不支持提交失败后当作成功。

统一锁顺序：安全域与策略控制行 → 按 ID 排序的人员/授权行 → 按 ID 排序的客户端/密钥控制行 → 申请行 → 执行行。只读元信息不持有不必要长锁；共享校验与独占变更对同一控制行发生冲突，从而把撤权与执行排序。死锁/序列化失败只允许有限重试不含外部副作用的事务。

## 5. 外部副作用

KMS/HSM、第三方签发及交付均不跨数据库事务持锁等待。采用“占用 → 调用 → 确认”模式，固定 operationId 和 manifestDigest；Provider 必须支持幂等或结果查询。返回超时不能证明未执行。最终确认必须 CAS 占用时目标 revision 与 owner_epoch，并重新检查阻断状态；停用或撤权后到达的成功响应不得恢复启用状态，远端已发生结果保留为隔离/待核对并审计。

UNKNOWN 时停止自动重试，保持待核对，不能清除占用再让另一个节点重做。fencing/owner_epoch 必须由实际受影响资源或 Provider 校验才有效；仅数据库记录一个数字不能阻止已经失联的旧执行器继续操作。无法 fencing 的 Provider 采用更保守的串行接管及人工核对，不能宣称透明自动故障切换。

审计 outbox 与业务状态同事务可靠写入；归档投递可重试且按 event_id 去重。独立归档尚未实现；普通认证高频事件采用受控汇总与风险审计，不强行把每次成功认证都变成大审计事务。

## 6. 现有表升级

现有已经实现：root_budgets、audit_events、approval_requests（草案+票重放）、replay_nonces、login_states、sessions。它们不能直接冒充完整目标模型。

- 后续迁移采用编号、校验和、版本账本及独立迁移身份；现有 schema.sql 的幂等建表用于开发初始化，不作为成熟生产迁移框架。
- 新字段先兼容添加；旧审批摘要/票属于旧 schema，明确失效并重建，不能静默升级摘要后继承票。
- 当前登录、会话已经有 profile_hash；升级不能恢复其失效占位值或旧会话。
- 老应用遇到不认识的状态/协议版本须拒绝，不忽略字段后继续授权；不做自动破坏性降级迁移。
- 迁移在独立临时 PostgreSQL 验证后再进入目标环境，生产 DDL 不由请求处理器执行。本次设计不执行任何迁移。

## 7. 验收及影响

阶段 2 重点验证：占用后应急停用再收到 Provider 成功响应不得恢复启用、跨环境关联拒绝、自然人去重、撤权与执行竞争、激活唯一性、时间边界、相同幂等键不同内容、审计失败回滚、nonce 原子消费、Provider 超时/重复回调/旧 owner、旧版本迁移不复活权限。

数据库故障、复制落后、网络分区及备份回滚仍需后续专门容灾验收；应用多实例不能代替数据库仲裁和安全恢复。

影响范围：本次只设计逻辑模型，未连接或修改任何现有业务数据库，未执行 DDL，未修改其他业务或 base 模块。正式网关和身份平台接入范围见《认证协议》的【其他业务影响待确认】。
