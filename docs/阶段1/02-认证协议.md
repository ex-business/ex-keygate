# 阶段 1.2：认证协议

日期：2026-10-19。状态：v1 协议选型与约束；尚无可用的业务认证接口或跨语言互操作认证。下述请求字段是拟定契约，不是已发布 API。

## 1. 按客户端类型分别配置

| 客户端 | v1 首选路径 | 秘密与身份边界 |
| --- | --- | --- |
| 可控后端 | HTTP Message Signatures + HMAC-SHA256 | 每客户端独立共享密钥，保存在可信服务端 |
| 桌面 | 外部系统浏览器 OIDC 授权码 + PKCE S256 | 不把安装包内静态 app secret 当秘密；本机凭据按实例隔离 |
| 移动端 | 系统浏览器 OIDC 授权码 + PKCE S256 | 同上；不把 clientId 当身份凭证 |
| 浏览器 | BFF 承接 OIDC，浏览器使用受控 HttpOnly 会话 | 不下发长期共享密钥，不在 localStorage 保存根密钥或长期认证秘密 |
| 硬件/设备 | 预留挑战与响应、设备内签名/验证 | 未接真实设备前明确不支持，不以模拟结果替代 |

用户身份、应用登记和安装实例身份是三件不同的事。OIDC 登录只证明用户身份；公开 clientId 只标识应用配置；设备持有证明只证明对应私钥的持有，除非另行验证硬件证明，不能声称证明官方应用未被修改。

现有 Profile 允许部分桌面/移动端 HMAC 组合，仅代表配置模型候选能力。v1 不默认启用这些组合；如需启用，必须先落实独立实例密钥的安全交付、真实存储及风控，不能使用所有安装共享的嵌入式密钥。该执行层限制尚待阶段 2 实现。

## 2. 后端请求签名

采用 [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html) 的 HTTP Message Signatures，算法固定为 `hmac-sha256`，不自创拼串签名算法。消息体摘要使用 [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530) 的 Content-Digest，v1 为 SHA-256。

拟定 v1 Profile：

| 内容 | 必须绑定的规则 |
| --- | --- |
| 签名标签及 Profile | 一个指定 v1 签名标签；拒绝多个冲突签名及未知 Profile |
| 请求目标 | @method、@scheme、@authority、@path、@query，按 RFC 派生和序列化 |
| 消息内容 | content-digest；有正文时同时覆盖 content-type，签署实际传输内容而非重编码后的 JSON |
| 业务身份 | x-keygate-client、x-keygate-key-version、x-keygate-audience、x-keygate-environment |
| 请求关联 | x-keygate-request-id；它是客户端签名关联值，服务端另生成审计 request ID，不混用 |
| 签名参数 | keyid、alg、created、expires、nonce、固定用途 tag；keyid 只用于查找，不授权算法或环境 |

完整字段编码、大小写和 Structured Fields 解析遵循 RFC；协议实施前还需产出精确头部示例及跨语言固定测试向量。不得只凭此表自行用不同语言各写一种“近似签名”。

边界规则：

- 算法与密钥从服务端 Profile 选择，alg 只做一致性检查；缺失或其他算法拒绝。
- 必需单值身份头重复即拒绝；不允许通过 Header/Trailer 两处取到不同值。v1 不支持 Trailer 签名。
- 原始路径、查询、百分号编码、空查询及重复参数严格按 RFC 处理；业务接口不接受的歧义查询应在签名前拒绝。不得先自行排序、解码、重新编码再验签。
- 验证端独立对实际接收正文计算 RFC 9530 SHA-256 摘要，并与 Content-Digest 比较，同时验证签名覆盖该摘要头；只验摘要头的签名不能证明正文未被替换。正文校验失败不消费认证成功状态。
- v1 不接受正文内容编码转换；无正文请求也定义空内容摘要，避免有无正文被不同端点解释。正文大小暂定上限 1 MiB，可通过受控 Profile 下调。
- 网关若改写 authority/path/query，必须在改写前完成验签，或通过受保护链路传递可信原始消息上下文；不能信任客户端可写的 X-Forwarded-*。

## 3. 时间、防重放与停用

项目暂定：`0 < expires-created <= 60 秒`，`created <= DB_now+30 秒`，且 `DB_now < expires`；超过 expires 不再额外延长 30 秒。nonce 为独立 32 字节随机值的规范 base64url 编码。

签名成功后，在权威数据库事务中重新读取启用状态、有效期、密钥及 Profile 修订，原子消费 nonce。nonce 作用域为环境、客户端、密钥和版本，保留至 expires；不得由客户端独立选择更短保留期。各节点共用同一判定，数据库不可用拒绝。

认证成功的线性化点为该事务提交；停用与认证对同一资源锁采用一致顺序。停用提交后才开始的认证必须拒绝；已先完成认证的业务请求不会被“追溯取消”，业务服务另需高敏感操作执行时复查或撤销机制。

重试分开处理：新尝试必须生成新 nonce 和签名；幂等业务沿用同一操作幂等键，不能因为重新签名而重复执行。只有 nonce 消费成功不代表业务操作成功。

## 4. 原生端与浏览器

原生应用采用 [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) 的外部用户代理模式及 PKCE，回调注册、state、nonce、issuer、audience 和短有效期均需验证。系统密钥库用于保护每实例材料，不允许所有用户共用一个 app secret。

需要访问资源 API 的原生端使用面向目标 API 的短期 access token；如启用 [DPoP / RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html)，必须完整验证绑定、公钥、方法/URI、jti、iat、ath 及必要的服务端 nonce。v1 暂不交付 DPoP 执行器，不能仅加一个签名头就宣称支持。ID Token 不作为资源 API access token。

浏览器延用已有开发 BFF 模型：Secure/HttpOnly/__Host- 会话、固定 Origin、CSRF、短绝对期限。生产真实 MFA、当前权限和浏览器兼容仍需验收；模拟 SSO 不能被当作这些能力已完成。

## 5. 认证结果的可信传递

业务网关/服务适配器从实际请求构造待验证上下文，通过受保护、受限身份的内部调用交给 ExKeyGate。认证结果绑定原始请求摘要、目标受众和有效期限，只在可信通道内使用；业务服务不能信任客户端提交的“认证成功 JSON”或身份头。

阶段 2 可先提供直接签署 ExKeyGate 探测接口的闭环，再实现正式网关适配。内部校验接口的方法/路径与结果编码尚未发布，后续单独定义；不在本阶段伪造现成接口。

外部错误统一区分：未通过认证 401；已认证但无相应本地权限 403；版本/幂等冲突 409；限流 429；权威设施不可用 503。内部保留安全原因码，不泄露密钥存在性或敏感材料。

## 6. 验收与影响

必须有仅替换正文而保留摘要头及签名的拒绝用例，以及跨语言固定向量、字段篡改、重复头、编码歧义、空正文、错误受众、错误算法、时间边界、跨节点重放、停用竞争和网络分区拒绝测试。当前代码只有部分 Profile、nonce 存储及开发 BFF，不代表已经实现该签名协议。

【其他业务影响待确认】正式接入涉及客户端 SDK、业务网关和资源服务：请求需增加签名或标准 Token 验证，错误处理和重试行为会改变。具体系统未选定，未修改或联调任何现有业务调用链。
