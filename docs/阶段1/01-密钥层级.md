# 阶段 1.1：密钥层级

日期：2026-10-19。状态：v1 设计决策，供阶段 2 实现；不代表下面的生命周期已经实现。现有开发保护器只用于登录 PKCE，不能当作客户端密钥服务。

## 1. 目标与边界

采用两层密钥，不额外堆叠没有明确用途的密钥层：基础包装密钥 KEK，客户端认证密钥。登录临时凭据单独分类，不与认证密钥混用。密钥来源可为内部 Provider、第三方或预留硬件 Provider。

| 材料 | 业务用途 | 持有者及保存 | 明文导出 |
| --- | --- | --- | --- |
| KEK：基础包装密钥 | 保护客户端认证密钥等秘密 | 生产 KMS/HSM；开发仅进程内随机生成 | 不提供管理导出接口，不下发客户端 |
| 客户端认证密钥 | 后端 HMAC 请求认证 | 客户端可信存储；服务端保存受保护密文或外部引用 | 仅受控首次交付；列表、详情、审计不返回 |
| 安装实例私钥 | 可选的设备持有证明 | 每安装实例生成，私钥留在本机密钥库/硬件；服务端保存公钥 | 服务端不索取私钥；首期仅预留 |
| 登录临时凭据 | state、nonce、PKCE、短会话 | 按用途生成独立随机值，秘密加密或仅存摘要 | 不通过运维查询接口展示 |
| TLS 私钥 | 加密传输及端点认证 | 独立证书管理 | 不复用 KEK 或 HMAC 密钥 |

密码学算法及密钥用途不可混用。未来若签发可跨服务使用的认证结果，必须使用独立结果签名密钥和协议，不能直接复用上述密钥。

## 2. 隔离与标识

- 每个环境、安全域、用途独立配置 KEK；`client_key_wrap` 与 `login_pkce_wrap` 使用不同 KEK。
- 每个客户端版本生成独立的 32 字节密码学随机 HMAC 密钥，不从 clientId、密码、时间或上一版密钥推导。
- KEK 的 rootId 指向不可变实际版本；禁止把同一 ID 静默指向新密钥，也不能给同一实际 KEK 分配多个预算来绕过限额。
- 所有查询及 Provider 运算绑定 `environment + clientId + keyId + keyVersion + purpose`。服务端从权威记录取绑定信息，不信任请求方自报用途或环境。
- 密文封套记录格式版本、Provider、不可变 KEK 引用及包装修订号。上述可信上下文参与认证保护，防止搬移到其他客户端或用途。
- 第三方不可导出密钥只保存引用；不要求把硬件密钥复制到软件节点，不在硬件不可用时自动回退。

## 3. 状态与生命周期

客户端密钥版本的目标状态：

| 状态 | 是否接受普通认证 | 进入条件 |
| --- | --- | --- |
| PENDING | 否 | 签发申请获批后创建并密封，尚未完成交付 |
| STAGED | 否 | 目标接收方完成领取与持有证明 |
| ACTIVE | 是 | 激活操作获批并执行，客户端同时处于启用状态 |
| RETIRING | 在明确过渡期内 | 轮换申请明确批准新旧并行时限 |
| DISABLED | 否 | 正常停用或应急停用 |
| COMPROMISED | 否，永久撤销该版本 | 确认泄露，禁止恢复 |
| EXPIRED | 否 | 数据库时间达到 notAfter；过期判断不能依赖后台任务及时改状态 |

v1 将签发与激活分成独立受控操作。签发成功不自动允许认证；将来合并操作必须在审批清单中明确全部副作用，不能悄悄增加激活行为。已停用或泄露版本不恢复，创建新版本替代。暂不提供不可逆销毁的业务入口。

KEK 状态区分 ACTIVE、UNWRAP_ONLY、BLOCKED、DESTROYED。正常轮换可进入 UNWRAP_ONLY 完成重包装；泄露的 KEK 必须 BLOCKED，并暂停受影响版本的正常认证，不能用“只解密”继续放行。灾备恢复属于独立多人控制流程。

## 4. 首次交付

1. 接收方证书/公钥指纹及目标客户端通过独立接入核验，并写入获批操作清单；管理员身份不能直接代替接收方身份。
2. v1 后端共享密钥仅经受保护的接入通道交付，例如已核验接收方的 mTLS。没有合格通道时保持 PENDING，不返回明文。
3. 交付事务绑定客户端、版本、接收方指纹和短有效期；普通管理员列表和详情只能看元信息。
4. 接收方对一次性 enrollment challenge 完成密钥持有证明后进入 STAGED。挑战必须绑定身份、版本、用途、随机 nonce 和过期时间，且全局只消费一次。
5. 接收响应丢失不声称“恰好展示一次”：服务端可以保证领取事务单次消费，无法保证网络接收方只看一次。无法确认时不重发同一秘密，停用该待激活版本后重新签发。

客户端保存材料后的导出与备份由相应接入策略约束；不受控终端不能因使用系统密钥库就宣称抵御完整设备失陷。

## 5. 两种轮换要分开

- 客户端密钥轮换：生成新的认证秘密与版本，客户端必须切换。过渡期由获批操作明确，旧版本到期立即拒绝。
- KEK 重包装：同一客户端秘密换用新的基础保护，不改变客户端 keyVersion；增加 wrapRevision，使用 CAS 防止覆盖并发停用或后续包装。
- 包装用量在加密前持久预留，失败/不确定结果不退款。软件 AES-GCM 的预算覆盖全部实例和恢复过程；生产由实际 KMS/HSM 能力另行约束。
- 备份恢复不能恢复已撤销版本或回退 KEK 使用预算；无法核对安全状态时暂停认证，不能用旧快照维持服务。

## 6. 现状、差距与验收

现有：AES-256-GCM 原语、关联数据绑定、软件开发保护器、数据库用量预算。尚缺：客户端密钥模型、交付证明、生命周期执行器及真实 KMS/HSM。

阶段 2 必须验证：跨环境/客户端/版本搬移密文失败；PENDING/STAGED/停用/泄露/过期拒绝；未获批不能激活；领取重放拒绝；根故障不降级；重包装不改变客户端秘密；轮换并发不会覆盖撤销。

参考：[OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)。具体分层与状态是 ExKeyGate 的设计选择，不是 OWASP 强制的枚举。
