<a id="renewal"></a>
## 业务证书续期

在服务行查看到期时间，点击「申请续期」导入 `renewal-proposal` 生成的公开 JSON。必须是已登记、未停用服务，固定根不能改变，新版本必须为当前版本加一，预期修订必须等于当前服务修订。新证书必须当前有效、根签名及用途正确、持有证明正确，并且到期时间晚于当前证书。

仍然由离线根签发，管理服务不接收业务私钥和根私钥。建议每次续期生成新业务密钥；新证书及私钥先部署到业务服务，执行切换时使用与新版本相符的签名。示例路径和标识须替换为实际值：

```sh
keygate-trust -action key-init -directory data/orders-v3
keygate-trust -action issue -directory data/orders-v3 -authority data/offline-root \
  -environment app-test -service orders-api -version 3 -hours 24
keygate-trust -action renewal-proposal -directory data/orders-v3 \
  -root-file data/offline-root/root.pem -environment app-test -service orders-api \
  -version 3 -revision 2 -output data/orders-renewal-v3.json
```

`-root-file` 是公开根证书路径；只有 `issue` 的 `-authority` 目录包含离线签发材料。生成的提案是公开证书和持有证明，不是业务私钥分发包。

```text
Generate key + offline issue
          |
          v
Import renewal proposal -> Sequential M-of-N -> Applicant executes
                                                   |
                                                   v
                                      Current version N -> N+1
                                      Old version -> retired
```

新版本执行后立即成为唯一当前版本，没有长期双版本认证重叠。旧版已签发状态证明最多保留原有30秒窗口。续期执行记录 `approved_renewal`，证书详情可追踪到审批申请。过期但未停用服务可以申请合法的新证书；已撤销或停用服务必须走明确的新版本发布恢复，不能用续期绕过恢复决策。根本身到期不能靠续期业务证书解决，须采用独立根恢复流程。

<a id="status"></a>
## 状态签名器受控更新

每个根有独立的状态签名器数据库指针与递增修订。证书中的状态用途协议版本继续为1，更新次数使用数据库 `revision`；两者不能混淆。

1. 从「信任链管理」查看当前状态证书指纹、到期时间、签名器修订和本节点材料装配情况。
2. 在可信离线环境用 `status-init` 创建新密钥和状态证书。新证书需延长有效期，且不得复用该根任何已登记历史状态签名密钥。
3. 在所有提供认证的节点预装新目录。`-trust-directory` 支持同根的多个不同候选目录；重复装配同一证书拒绝启动。只有材料已加载并不等于获批，也不能让它自动生效。
4. 用 `status-proposal` 生成公开提案，导入「导入状态证书更新提案」。申请人和审批人必须有全域对应角色，单个服务范围的授权不足。
5. 逐人审批后由申请人执行。执行时重新检查证书有效期、持有证明、人员权限和当前修订，当前指针和历史记录在同一事务提交。
6. 节点在每次状态签发事务中读取批准指纹，只能选择对应已加载材料。缺少新材料的旧节点拒绝服务；不得回退旧签名器或缓存认证结果。
7. 查看「状态证书变更记录」和关联申请，确认修订及指纹。页面的材料状态仅代表本次请求所在节点；必须逐节点检查，不能当作集群就绪报告。

```sh
keygate-trust -action status-init -directory data/status-next \
  -authority data/offline-root -environment app-test -hours 24
keygate-trust -action status-proposal -directory data/status-next \
  -root-file data/offline-root/root.pem -environment app-test -revision 1 \
  -output data/status-next-proposal.json
```

将新目录安全分发到节点，确保不包含 `root.key`。`status.key` 属于该状态服务运行材料，不得放入提案或通过管理网页上传。启动配置示意：

```text
-trust-directory data/status-current,data/status-next,data/another-root-status
```

首次可信启动为尚未登记签名器的根登记初始证书，并记录离线初始化事实；以后重启、装载候选目录均不会覆盖数据库批准指针。迁移后的首次装配必须由授权运维指定初始目录，所有节点使用同一套初始配置，不能让不同候选竞相初始化。

切换指针约束的是受控服务端签发，不能使客户端立即拒绝攻击者用已泄漏状态私钥自行生成的签名。客户端仍根据固定根验证状态证书；怀疑状态私钥泄漏必须采用独立恢复通道更换信任根，不能把普通状态证书续期宣传为泄漏恢复。已发证明、网络中的外部请求及操作系统特权回滚也不因此消失。

<a id="reminders"></a>
## 到期提醒与插件

服务每分钟根据数据库时间扫描当前应用根、当前状态证书，以及未停用服务的当前活动业务证书。分级为7天内、24小时内、1小时内、已过期；相同证书与级别只建一条记录。晚启动只创建当前紧急级别，不补发所有较低级提醒。换版、停用或撤销会取消尚未完成的旧提醒；已发送记录保留。

未配置插件时，页面保留「待发送」。配置插件后按队列发送，插件负责受控收件人配置、邮件/短信渠道，以及同一 `Idempotency-Key` 的幂等投递。KeyGate不接受页面指定任意收件人。插件确认接收并不代表短信或邮件最终送达；最终投递回执由渠道插件维护。

通过 `-trust-reminder-plugin-file` 指定私有 JSON 配置，密钥必须为私有普通文件。示例为占位地址，不能直接投递：

```json
{
  "url": "https://notify.example.invalid/certificate-expiry",
  "allowedIPs": ["192.0.2.20"],
  "caFile": "/secure/notify-ca.pem",
  "certificateFile": "/secure/notify-client.pem",
  "keyFile": "/secure/notify-client.key"
}
```

固定IP拨号、专用CA、TLS1.3、客户端证书、主机名校验、禁代理和禁重定向共同约束插件。重试正文只包含以下不可变公开字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定幂等键，与 `Idempotency-Key` 一致 |
| `rootFingerprint` | 所属根 |
| `serviceId` | 业务服务、`trust-status` 或根的空标识 |
| `kind` | `root`、`status`、`service` |
| `fingerprint` | 到期证书的SHA-256指纹 |
| `expiresAt` | 证书到期时间 |
| `severity` | `due_7d`、`due_24h`、`due_1h`、`expired` |

HTTP POST返回200或204才确认接收；202、重定向、错误及超时均保留重试。同一幂等键正文在重试时保持不变，尝试次数和队列内部状态不发给插件。

外部调用不持有数据库锁；60秒租约、10秒调用超时，失败5分钟后重试。每节点每轮最多处理2条，实际大规模吞吐须另行容量验证。多节点可同时扫描和处理；唯一约束、租约与尝试编号限制重复领取和迟到回写。外部请求已发出时发生换版或取消，无法收回在途邮件；插件必须幂等，不能声称恰好一次送达。配置文件仅在启动时读取，变更需受控重启。

<a id="api"></a>
## 接口与字段

| 方法及路径 | 返回与权限 |
| --- | --- |
| `GET /api/trust/services` | 根及业务服务目录新增 `info`，包括到期时间；沿用Viewer范围隔离 |
| `GET /api/trust/status-signers` | 全域Viewer：`signers` 和当前节点 `nodeReady`；最近50条 `changes`，截断时 `changesHasMore=true` |
| `GET /api/trust/reminders` | 全域Viewer：最近200条 `reminders`，截断时 `hasMore=true` |
| `POST /api/requests` | 复用已有审批申请；续期 `kind=trust_certificate_renew`，状态更新 `kind=trust_status_update` |

以上新增GET目录不接受查询参数，拒绝任意 `?limit=` 等参数。均须登录、本人MFA、有效人员及当前权限。提醒保留 `pending/sending/sent/superseded` 与尝试次数；页面只提供状态查询，不提供随意更改发送结果的接口。

续期提案沿用公开发布字段；`clientId` 为业务服务，`keyVersion` 为下一版本，`expectedRevision` 为当前服务修订。状态更新 `clientId` 固定为 `trust-status`，`keyVersion` 固定字符串 `"1"`，`expectedRevision` 为当前状态签名器修订，根指纹、公开证书与持有证明必填。版本及修订字段使用十进制字符串，服务端重新验证，不能依赖页面预览。

409表示当前状态已变化，应重新读取并生成提案；不得悄悄替换已冻结申请的内容。证书在审批期间过期、根不匹配、私钥持有证明错误、旧密钥重用或新有效期未延长时，不能执行。执行响应丢失可使用原申请ID与摘要核对及重试，不创建新申请冒充原操作。

<a id="operations"></a>
## 部署、升级与边界

迁移18新增状态签名器、变更及提醒表，纳入安全检查点；旧迁移校验和不变。先备份、停止旧应用节点、统一升级并核验初始签名器，再开放流量；不承诺新旧二进制混跑。旧安全检查点不能覆盖新表状态，须升级后重新捕获和独立归档。升级后不直接降级旧程序。

当前 `keygate-dev` 默认仍创建新的隔离开发域；不是保持原域的正式重启方案。预装候选、集群切换测试应使用同一权威域的服务实例；不得通过重启开发演示假装保留原业务数据。正式启动持久化仍为KG-06。

【涉及其他业务】扩展共享审批分发和全域角色解析，增加审计事实及安全检查点表；共享密钥、H5、插件和人员验证逻辑本身不迁移。对应数据库与HTTP回归、竞态测试、开发安全验收须通过。真实邮件/短信厂商、集群滚动部署及生产容量/灾备未在本批验收；KMS/HSM仍按既定计划预留，生产门禁不解除。
