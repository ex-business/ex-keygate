# 审批通知运维

入口：管理页 → 审批中心 → 通知运维。全域策略管理员、全域审计员完成本人验证后可查询；局部授权不开放全域队列。个人收件箱继续只显示本人通知。

## 查询与投递记录

按失败、等待、发送中、已确认接收、已失效筛选，每页50条，最多查询前10050条。当前采用偏移分页，任务状态变化可能导致翻页重复或跳过，刷新重新查询。显示申请、收件人、当前状态、本轮尝试次数及人工重发轮数。

“投递记录”保留每次实际发送的开始/完成时间、轮次、尝试编号和结果；人工重排额外保存操作人、原因及时间。进程中断后的租约超时标记为结果未确认，不视为未送达。只显示固定结果分类，不保存插件响应正文、收件地址或凭据。升级前没有逐次记录的历史不补造。

HTTP200/204仅代表插件确认接收，不等于用户已读或厂商送达。旧请求已经发出后不能撤回；迟到回应不能恢复失效任务。

## 受控重发

仅全域策略管理员可操作，需要近期身份验证和有效本人验证；填写3至500个UTF-8字节的原因，勾选确认后提交。审计员不能重发。

仅对仍有效的 `failed` 通知开放。再次核验原申请摘要、收件人的冻结资格和通知当前用途；已经交接、过期或撤回导致旧待办失效时拒绝重发。当前有效的终态结果通知不因业务申请结束而失效。发送中、已确认或已失效任务均不能手动重排。

每轮自动尝试最多5次，人工最多3轮，两次人工重排间隔至少60秒。重排保留原通知ID、插件幂等键与通知载荷，不删除旧记录；新轮次独立计数，迟到的旧轮次回应不能覆盖新轮次。同一操作人、原因、摘要和预期轮次重复提交按同一次操作处理。服务端仍会重查身份，不能用幂等重试绕过撤权。

这是通知投递运维，不重新批准申请，也不增加审批票或改变业务密钥状态。插件必须按原ID持久去重：先前实际已接收但确认丢失时，人工重试可能只得到原投递结果。

## 积压告警

后台约每10秒检查，面板显示检查时间与触发/恢复状态：

| 告警 | 当前阈值 |
| --- | --- |
| 投递积压 | 等待任务至少100条，或最老等待至少5分钟 |
| 失败任务 | 失败任务大于0 |
| 租约超时 | 发送中的30秒租约已过期 |

状态变化在数据库提交后记录中文结构化日志，包含管理域、告警代码、计数和最老等待秒数。持续异常不重复刷屏，恢复记录单独日志。页面读取最近后台检查结果，应留意检查时间；所有节点停止或数据库失联时无法更新面板，需由外部监控检查服务就绪和日志采集。当前未接短信/邮件值班通知或外部监控平台，阈值固定，不支持页面调整。未配置通知插件仍可能产生积压告警。

## 接口

| 方法与路径 | 参数与行为 |
| --- | --- |
| `GET /api/notification-operations` | `state`可选，`offset`为0至10000；返回 `items/alerts/more/canResend` |
| `GET /api/notification-operations/{id}/records` | 同全域只读权限，返回逐次记录 |
| `POST /api/notification-operations/{id}/resend` | `digest`、`reason`、`expectedRound`必填，成功204 |

写接口要求同源和 `X-CSRF-Token`，未知JSON字段拒绝。查询参数只支持白名单，不支持重复参数。403表示权限或验证不足；409表示状态、轮次、摘要或冷却期冲突，刷新后核对，不自动改轮次重试。重排记录和审计在同一事务中保存。

## 升级及影响

【涉及其他业务】新增schema23的投递历史、告警表和通知人工轮次；检查点覆盖新增数据。支持原schema21或22通过停服、最新外部签名检查点升级至23，DDL、发布修订和节点代次整体提交，普通run不迁移，不支持降级。原审批、领取、认证协议保持不变；通知发送与重排继续使用同一域锁和节点隔离约束，外部I/O不持业务事务锁。
