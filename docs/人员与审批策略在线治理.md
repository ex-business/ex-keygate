<a id="use"></a>
## 日常操作

### 登记人员

管理人员登录并完成本人验证，在「人员与权限」点击「登记管理人员」，填写已接入身份源的准确issuer、subject、自然人标识、变更原因及身份核验记录SHA-256。自然人标识使用组织核验后的固定标识，不能把邮箱、昵称或另一人的账号随意拼接为身份。

申请由当前策略的不同人员依次验证、核对并确认，达到当前门槛后，由原申请人执行。登记成功显示在人员列表，初始没有管理角色，也不创建密码、TOTP、邮箱、手机号或硬件绑定。本人验证及实际登录账号准备仍使用已有受控流程，后续自助维护属于KG-05。只有登记记录不能登录取得管理权限。

只允许登记已存在于本管理域的issuer，新身份主键由issuer/subject计算，不接受调用方直接指定。拒绝重复身份和在线重复自然人标识；不提供在线替换issuer/sub或自然人归属的功能。既有多身份别名可以分别显示，单条记录的启停和授权针对该身份主键，不宣称停用一条记录会停用同一自然人的所有别名。

### 调整角色、范围及人员状态

在目标人员行点击「调整人员与授权」，核对身份主键与当前修订，选择启用或停用，编辑完整授权清单，再填写原因和证据摘要后提交审批。

清单完整替换此身份的全部角色范围，移除某一行意味着撤销该项授权。停用状态与保留的授权分别展示：停用后所有授权均不可使用；恢复需要重新审批，不能直接点击恢复生效。人员调整执行后，当前管理域中调整前已经存在的登录会话被封禁，旧本人验证和关联旧票失效，H5会话受人员修订校验。此人须重新登录并完成本人验证。

现有六类角色继续沿用，不创建任意新角色或人类执行器权限：

| 角色 | 作用 | 范围 |
| --- | --- | --- |
| `viewer` | 资源查看 | 全域或已登记客户端/业务服务 |
| `requester` | 发起业务申请 | 全域或已登记客户端/业务服务 |
| `approver` | 参与审批 | 全域或已登记客户端/业务服务；参与全域策略名单须有全域角色 |
| `policy_admin` | 策略及人员治理资格 | 必须全域；发起治理同时需要全域Requester |
| `auditor` | 审计查询 | 全域或已登记客户端/业务服务；组织完整目录还需全域Viewer |
| `emergency_operator` | 紧急减权 | 本在线授权入口只允许配置全域；不会授予绕过审批的增权能力 |

非空范围必须是当前域中已登记的客户端或信任链业务服务标识。空字符串只表示当前管理域全部资源，不是跨域通配符。治理页面要求全域Viewer读取人员目录，并由全域PolicyAdmin和Requester共同取得申请资格。普通全域Viewer不能读取他人的组织治理申请快照；当前申请人、冻结且仍有资格的审批人，以及全域Viewer加PolicyAdmin/Auditor按对应边界读取。

### 变更审批策略

在「审批策略」点击「申请变更审批策略」，编辑候选名单、上下移动顺序和M值。加入名单的身份必须已启用、具有全域Approver；启用原生验证的域还要求已配置本人验证。

新策略仍由当前策略审批，不能直接使用新名单批准自己。至少2名、最多32名不同自然人，M不能超过N。执行后强制采用逐人交接模式并增加策略版本。界面显示新版本和新顺序，旧策略下未执行申请显示「策略已变更」，需要按新策略重新申请。

```text
Personnel / role / policy change
              |
              v
Current policy freezes members + revisions + manifest digest
              |
              v
Person 1 verifies -> confirms -> Person 2 verifies -> confirms
              |
              v
Original applicant executes -> Recheck live permissions and revisions
              |
              +--> Personnel: replace grants + revise identity + block old sessions
              |
              +--> Policy: new version + new ordered members
```

<a id="rules"></a>
## 权限与审批规则

- 全域Requester和PolicyAdmin均在申请中冻结其资格，执行时再次核验；撤权后重新授予不会让旧冻结资格自动恢复。
- 不允许申请人调整自己或同一自然人的其他身份。目标身份所属自然人也不参加本次人员调整表决，其所有别名一并回避。回避后人数不足，拒绝申请，不自动降低门槛。
- 人员调整不能破坏当前策略名单的全域Approver资格；若要停用或撤销在任审批人，先新增合格人员并经过当前策略批准替换名单，再调整原人员。
- 变更后的每个候选必须是已启用、不同自然人的全域Approver；不得用同一人的不同账号凑N。
- 必须保留至少一位位于审批名单之外、可独立发起治理的已启用全域Viewer+Requester+PolicyAdmin；原生验证域还需已配置MFA。不能把组织改到没有可独立发起的管理者。
- 全部变更按安全域行锁串行，与撤权、投票及执行使用同一事务边界。人员或策略状态与审计同事务，审计失败整体回滚。
- 证据摘要只用于关联组织核验记录，系统不据此宣称已经验证真实员工身份或真实人工签名。不要在原因、subject或证据字段填入密码、token、验证码或私钥。

<a id="api"></a>
## 接口与字段

复用 `POST /api/requests`、`POST /api/requests/{id}/votes`、`POST /api/requests/{id}/execute`，沿用登录Cookie、同源Origin、CSRF和申请幂等键。审批交接和放弃继续使用现有接口。

| 操作 | `kind` | `expectedRevision` |
| --- | --- | --- |
| 登记人员 | `principal_create` | 字符串`"0"` |
| 完整替换启用状态及授权 | `principal_update` | 当前人员`revision`字符串 |
| 修改审批策略 | `approval_policy_update` | 当前策略`version`字符串 |

`clientId`固定为`governance-management`；`name/profileId`为空，`profileVersion`为`"0"`，不能夹带共享密钥、插件或信任链字段。

`governance`公共字段：`reason`为3至500字节无控制字符的变更说明，`evidenceHash`为64位小写十六进制摘要。

| 场景 | 其他字段 |
| --- | --- |
| 登记 | `issuer`、`subject`、`personId`；`enabled=true`；不允许附带授权 |
| 人员调整 | `target`为身份主键；`enabled`为目标状态；`grants`是完整`[{"role":"viewer","clientId":""}]`清单，空清单撤销全部角色 |
| 策略 | `enabled=false`；`m`为门槛；`approvers`是有序身份主键数组；不接受人员身份或授权字段 |

示例仅为公开协议占位，身份及摘要须换为组织已核验记录：

```json
{
  "kind": "principal_update",
  "clientId": "governance-management",
  "expectedRevision": "3",
  "name": "",
  "profileId": "",
  "profileVersion": "0",
  "governance": {
    "target": "oidc-<实际64位身份摘要>",
    "enabled": true,
    "grants": [{"role": "viewer", "clientId": "orders-api"}],
    "reason": "调整运营人员查看范围",
    "evidenceHash": "<实际64位核验记录摘要>"
  }
}
```

`GET /api/console/settings`新增每人`revision`、`issuer`和`mfaConfigured`，仍不返回密码、验证种子或绑定地址。人员清单最多128条，在线登记总人数也限制为128（包含停用身份）；不提供硬删除以清空审计历史。授权清单每身份最多64项。

申请查询新增`invalidated=true`表示策略版本已经变化；字段用于展示，授权结果仍以投票和执行时的完整服务端复查为准。因人员修订或角色变化失效的旧票也会在执行时被拒绝，不能仅根据页面是否显示此字段决定可执行。

<a id="states"></a>
## 生效、失效与异常

- 申请成功返回201，尚未变更人员或策略；达到审批门槛也不自动执行。原申请人执行成功沿用200响应。
- 重复执行原已执行申请及相同摘要保持幂等；网络结果不明先查询原申请，不换新幂等键重复提交。
- 400：非法角色/范围、重复授权、未知字段、非法门槛或证据格式等，应修正后重新申请。
- 403：缺少全域资格、修改本人、受益人回避后不足门槛、破坏管理或审批可用性等；不能通过前端隐藏字段绕过。
- 409：人员/策略修订已变化、重复人员、无实际人员变更或已冲突；刷新核对，不修改已冻结申请内容。
- 人员状态、角色修订或审批策略在审批期间改变，票和执行资格重新检查；不重用旧审批记录批准新的内容。
- 连续治理沿用同一验证器五分钟最多五次核验的限制，成功核验也计入额度；跨会话、申请和节点共享，重新登录不会重置额度。达到限制后等待窗口恢复，不能靠重建绑定绕过。
- 被调整者即使在SSO会话中携带略微超前的`auth_time`，其原管理Cookie也会被域内会话封禁记录拒绝；不是靠客户端或外部时间推断发行先后。其他管理域中同一身份的独立会话不随本域调整撤销。

<a id="operations"></a>
## 升级及验收

迁移19新增按管理域隔离的`principal_session_blocks`，纳入安全检查点；不修改旧迁移校验和。先备份并停旧节点、统一升级及捕获新检查点，不承诺新旧程序混跑或旧检查点完整覆盖新状态。

【涉及其他业务】共享审批分发及组织快照读取、管理身份解析、旧管理会话、MFA、H5、审计范围与安全检查点。新增人员接口不会修改SSO平台、创建密码或绑定验证器。人员调整使该身份在当前域的既有管理会话和依赖人员修订的H5会话失效；其他域不受此会话封禁表影响。

本批验证包含数据库事务和竞态、未来auth_time旧会话、跨域隔离、普通Viewer组织信息隔离、管理员撤权及重新授予、受益人回避、策略旧票拒绝，以及真实浏览器三身份逐人审批、人员启停授权和策略顺序调整。真实SSO厂商、组织员工真实性、生产集群和KMS/HSM仍按已有生产门禁验收，不因新增页面解除限制。
