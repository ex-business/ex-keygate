# 内部密钥保护基础

状态：仅实现进程内加密原语及测试，未接入持久化、密钥托管、审批执行器或对外接口，不是已部署的密钥库。

## 当前实现

- 使用 Go 标准库 AES-256-GCM；随机数由密码学安全随机源产生，不自行实现算法。
- `Generate` 生成 32 字节随机密钥；`New` 要求外部提供 32 字节包装密钥，无默认密钥或自动生成的持久根密钥。
- 包装密钥 ID 必须标识一个不可变版本，不可在保留相同 ID 时替换原始密钥。
- 密文使用关联数据绑定环境、客户端、密钥 ID、版本和用途，并绑定格式及根密钥 ID，拒绝跨作用域替换。
- 每个密文保护一把 32 字节客户端密钥；固定长度限制畸形数据和异常分配。
- 解密失败不返回部分明文，向调用者统一返回失败。

使用的 [Go NewGCMWithRandomNonce](https://pkg.go.dev/crypto/cipher#NewGCMWithRandomNonce) 自动生成并携带随机 nonce。官方要求同一密钥加密消息数量不能超过 2^32；生产接入前必须通过权威持久化设施管理全局使用预算，预算严格低于该上限，覆盖所有节点、轮换和备份恢复，不能用单进程计数器替代。

## 必须后续落实

1. 基础密钥来自独立可信托管，不与业务密文同库保存，不写入 Git 或普通配置文件。具体托管设施待技术设计确认。
2. 包装调用前完成全局用量额度预留、操作授权和审计记录，失败调用保守消耗额度，不回收可能已经使用的额度。
3. 解密使用的 Binding 来自可信数据库及授权上下文，不信任密文提交方自报的环境和客户端。
4. 密文完整性不等于防回滚：仍需权威版本、停用状态和受控备份恢复机制。
5. 调用方限制明文生命周期，禁止记录或序列化明文；托管内存及 AES 密钥展开不承诺绝对零化，不能宣称抵御服务器完全失陷。
6. 硬件模式不可用时不调用软件模式作为隐式备用。设备密钥不可导出能力只有真实设备接入后才能验证。

## 已验证

随机 nonce、往返、错误根密钥、关联数据每个字段替换、密文逐字节篡改、畸形长度、未知格式、空对象及并发调用。未验证真实 KMS/HSM、备份恢复、持久化预算和生产安全等级。
