# 应用信任链与 Go 接入

用于自己的应用固定根证书、验证服务端签名。服务端业务私钥泄露后，撤销旧证书并审批发布新版本；客户端继续使用原根证书。

<a id="scope"></a>
## 范围与角色

本期交付 `trustchain` Go 包、`cmd/keygate-trust` CLI、管理页面及共享 PostgreSQL 治理状态。CLI 网络入口暂限本机 HTTPS；远程生产执行器、移动端及桌面 SDK、KMS/HSM 尚未交付。

| 角色 | 持有内容 | 操作 |
| --- | --- | --- |
| 离线签发方 | 应用根私钥 | 签发业务证书和独立状态证书 |
| 业务服务端 | 本服务私钥、证书 | 接收挑战并签名正文 |
| 管理服务 | 根公证书、状态私钥和证书 | 多人审批发布、查询权威状态、签发短时状态证明 |
| 客户端 | 固定根公证书、独立恢复公钥、持久状态 | 同时验证业务签名和状态证明 |
| 独立恢复方 | 与根私钥分开保管的恢复私钥 | 根泄露后签署更换根的更新 |

应用根不加入操作系统信任库，不用于网站 HTTPS。HTTPS 证书、存储加密根与应用签名根各自独立。信任链也可通过签名清单实现；这里选择 X.509 作为统一证书格式。

```text
Offline root --> Business certificate --> Payload signature --> Client
             --> Status certificate --> Fresh status proof --> Client
Recovery key --> Root update -------------------------------> Client
```

<a id="setup"></a>
## 配置与发布

以下为开发演示，各目录应隔离且权限为 0700，私钥为 0600；不要把 `data`、私钥、密码或账号配置提交到 Git。先在仓库根目录构建：

```sh
go build -o /tmp/keygate-trust ./cmd/keygate-trust
```

初始化离线根与独立恢复密钥，分别保管：

```sh
/tmp/keygate-trust -action root-init -directory data/app-offline-root
/tmp/keygate-trust -action recovery-init -directory data/app-offline-recovery
```

生成管理服务运行目录。此开发命令需要同时访问根目录，完成后仅把运行目录部署到管理节点；根私钥不能部署到管理节点。

```sh
/tmp/keygate-trust -action status-init \
  -authority data/app-offline-root -directory data/app-runtime -environment app-test
```

运行目录包含 `root.pem`、`status.pem`、`status.key` 和 `runtime.json`。管理台在原有账号、MFA 和数据库配置基础上追加 `-trust-directory data/app-runtime`。该目录含 `root.key` 时启动失败。每个管理安全域支持多个独立根。根指纹是稳定标识，每个根绑定一个应用环境，重复登记同一根时环境必须完全一致。每个业务服务在域内使用唯一标识并固定绑定一个根，普通轮换不能换根。

在业务服务器生成私钥和 CSR：

```sh
/tmp/keygate-trust -action key-init -directory data/app-server-v1
```

只把 `service.csr` 交给离线签发方。以下命令读取指定目录中的 CSR 并写入 `certificate.pem`，不需要业务私钥。实际隔离部署应在离线机的独立 CSR 目录执行，再把证书交回服务器。

```sh
/tmp/keygate-trust -action issue -authority data/app-offline-root \
  -directory data/app-server-v1 -environment app-test -service api-service -version 1
```

业务服务器生成只含公开证书和持有证明的发布提案：

```sh
/tmp/keygate-trust -action proposal -directory data/app-server-v1 \
  -root-file data/app-offline-root/root.pem -environment app-test \
  -service api-service -version 1 -revision 0 -output data/app-proposal-v1.json
```

管理台「密钥管理 → 应用信任链 → 导入证书发布提案」选择该 JSON。申请人完成管理 MFA 后提交；审批人依次完成该申请的本人验证并批准；达到 M 人同意后，由申请人确认执行。**发布执行同时启用新证书**。未经执行，证书即使已离线签发也不能通过在线状态核验。

`revision` 必须等于页面当前修订，新服务首次为 0；`version` 必须为当前版本加 1。修订冲突后重新查询、生成提案和审批，不能修改已批准申请的内容。

### 多个独立根

每套根单独执行 `root-init` 和 `status-init`，分别保管根私钥与运行目录。启动时通过逗号列出所有运行目录：

```sh
# 在原有数据库、账号、MFA、SSO、TLS 参数基础上追加。
go run ./cmd/keygate-dev -enable-key-flow \
  -trust-directory data/internal-runtime,data/partner-runtime,data/device-runtime
```

每个目录包含自己的 `root.pem`、`status.pem`、`status.key` 和 `runtime.json`。同一应用环境也可配置不同根，但客户端仍必须固定指定根；管理服务不会合并成一个通用信任池，也不会让根互签。

```text
Internal root --> orders-api certificate --> Internal client
Partner root  --> partner-api certificate --> Partner client
Device root   --> device-api certificate --> Device client
```

管理台按根分组显示环境、完整指纹及业务服务。公开提案自带根指纹，导入时检查其根已配置，服务端再检查证书签名与绑定；各链独立审批、发布和撤销。客户端为各用途使用独立 pin 配置或状态目录；不能把多套根作为“任意一个通过即可”的回退规则。

根的首次增加仍是受控离线启动配置，不提供通过页面上传根私钥的入口。业务服务标识在管理域内唯一；例如两个根下不能同时登记同名 `orders-api`，应使用不同服务标识。

<a id="verify"></a>
## 客户端验证

通过应用安装包或可信配置渠道预置根和恢复公钥，并核对指纹；不能从待验证业务服务器首次下载后自动信任。初始化只执行一次，拒绝覆盖已有状态：

```sh
/tmp/keygate-trust -action pin-init -directory data/app-client \
  -root-file data/app-offline-root/root.pem \
  -recovery-public data/app-offline-recovery/recovery-public.json \
  -environment app-test -service api-service -audience demo-client
/tmp/keygate-trust -action challenge -directory data/app-client
```

把返回的 `nonce` 发送到业务服务器。服务器对同一份正文和该 nonce 签名（将 `<nonce>` 替换为返回值）：

```sh
/tmp/keygate-trust -action sign -directory data/app-server-v1 \
  -root-file data/app-offline-root/root.pem -environment app-test \
  -service api-service -version 1 -audience demo-client -nonce '<nonce>' \
  -payload-file data/payload.txt -output data/app-message.json
```

客户端接收正文和消息，访问管理状态服务核验。`-ca-file` 是 HTTPS CA，不是应用根；使用开发控制台输出目录实际生成的 `ca.pem`：

```sh
/tmp/keygate-trust -action verify -directory data/app-client \
  -input data/app-message.json -payload-file data/payload.txt -nonce '<nonce>' \
  -origin https://localhost:18761 -ca-file data/dev-console/ca.pem
```

成功返回 `verified: true`、业务 `version`、权威 `revision`。任何错误都拒绝认证，不能回退为“只验签”。同一挑战成功后不能重复使用；超时重新生成挑战和业务消息。验签只证明指定服务持有有效密钥并签署了指定正文，不代替业务权限判断。

Go 调用方可使用 `InitializeClient`、`OpenClient`、`Challenge`、`Verify` 和 `Close` 获得同样的持久验证逻辑；通过 `DecodeJSON` 解码外部消息。`Verifier` 支持自定义 `StateStore`，其 `Accept` 必须原子保存修订水位并消费挑战；存储失败必须返回错误。`MemoryState` 仅用于进程内测试，不能作为跨重启客户端的持久防重放存储。

<a id="recovery"></a>
## 轮换、撤销与根恢复

业务私钥泄露时，拥有应急权限的管理员完成 MFA 后在该服务行点击「泄露撤销」，核对版本并确认。状态立即提交为停用，旧版本永久保持撤销；已签发的状态证明最多仍有 30 秒有效期。

生成全新 `app-server-v2` 私钥和 CSR，离线签发 `version 2`，按页面新修订生成提案，再走多人审批和执行。正常轮换也使用同一流程。新版本执行后旧活动证书退休，没有双版本重叠窗口；客户端固定根不变。普通「申请停用」需要多人审批。

如果根私钥泄露，仅靠旧根签发“新根”无法恢复信任。必须使用客户端事先固定的独立恢复公钥：

```sh
/tmp/keygate-trust -action root-init -directory data/app-new-offline-root
# 在独立恢复机执行；directory 是可信客户端 pin 状态的受控副本，不是在线客户端磁盘挂载。
/tmp/keygate-trust -action recovery-sign -directory data/app-client-pin-copy \
  -authority data/app-offline-recovery -root-file data/app-new-offline-root/root.pem \
  -output data/app-root-update.json
# 通过独立可信运维或应用更新渠道分发后，在客户端执行。
/tmp/keygate-trust -action recovery-apply -directory data/app-client -input data/app-root-update.json
```

更新绑定旧根指纹、新根及严格加一的 epoch，最长有效 24 小时；重复、越级或旧根私钥伪造的更新被拒绝。应用更新原子替换本地根和 epoch，清空待用挑战及旧修订水位。攻击者若阻断更新分发，无法保证客户端自动恢复；独立恢复私钥也泄露时须另行可信软件更新。

当前管理安全域的根不可原地替换。根恢复后需建立新的隔离管理域，部署新状态证书，重新审批发布业务证书，再切换客户端状态入口。多根域内其他根可以继续独立使用，但受影响服务的根绑定仍不能通过普通轮换修改。没有实现生产级同域在线根迁移编排。

<a id="protocol"></a>
## 协议与接口

证书为 Ed25519 X.509：根自签且禁止中间 CA；叶证书直接签发，URI SAN 为 `keygate:<environment>:<purpose>:<service>:<version>`。用途分别为 `service-signing`、`status-signing`；状态服务固定 `trust-status` v1。校验使用显式根池，不信任系统根或远程补链。

签名采用受限 JCS 规范化 JSON，删除 `signature` 后加用途前缀：`keygate-application-trust-v1/message`、`/status`、`/root-recovery`，前缀末尾接一个 NUL 字节。持有证明签署同协议 `/possession`、NUL 和证书 SHA-256 小写十六进制指纹。字节字段使用标准 Base64，nonce 为 32 字节随机数的无填充 Base64URL；版本和修订不超过 2^53-1。外部 JSON 拒绝重复键、未知字段、大小写别名和尾随内容。

| 字段 | 客户端决策 |
| --- | --- |
| environment / serviceId / audience | 必须与本地固定用途完全相同 |
| nonce / payloadHash | 必须匹配当前本地挑战和正文 SHA-256 |
| certificate / version | 必须通过根链与用途校验，且匹配状态中的当前版本和证书指纹 |
| revision | 不得小于已持久化修订 |
| disabled | 为 true 时拒绝 |
| issuedAt / expiresAt | 使用可信本地时间校验，业务消息最多 60 秒，状态最多 30 秒 |

- `GET /api/trust/services`：管理会话、本人 MFA、查看权限；返回 `roots` 数组及当前可见服务版本、修订、`rootFingerprint` 和停用状态。全域查看者可见未发布业务证书的根，范围查看者只能看到有权服务关联的根。
- `POST /api/trust/{service}/status`：公开、限流，正文为 `{"nonce":"<nonce>","audience":"demo-client"}`。返回独立签名状态；公开信息不包含私钥。数据库不可用时拒绝，不能返回缓存成功。状态读取、数据库时间和签名处于同一权威事务，提交成功后才返回证明。
- `POST /api/trust/{service}/revoke`：会话、CSRF、本人 MFA 和应急角色；正文 `{"version":1,"reason":"confirmed_leak"}`，成功 204。版本冲突或权限失败时不撤销其他版本。
- 发布及普通停用复用现有 `/api/requests` 申请、逐人验证、投票与执行接口；公开提案包含根指纹、证书和私钥持有证明，不含业务私钥。

<a id="limits"></a>
## 边界与验收

根有效期 1 年；开发业务证书和状态证书最长 24 小时，过期拒绝，续签需提前安排。状态签名密钥与业务私钥分开；状态密钥泄露仍需隔离签名节点、重新签发状态证书并评估客户端恢复。多节点共享同一权威数据库，不能各自使用独立可写数据库提供状态。

CLI 状态使用私有文件、独占锁、原子替换和 fsync。丢失状态、时钟回退、容量超限或锁冲突时拒绝；不自动抢占遗留锁，人工确认没有活进程后处理。普通文件不能抵御拥有磁盘管理权限的攻击者回滚整个状态，生产应使用受保护的单调存储。操作系统与本地时间必须可信。

数据库迁移 15 建立应用信任链，迁移 16 扩展多根并为已有服务保留原根绑定；升级后重新生成检查点，旧检查点不能直接恢复新增表或字段。升级应停止旧节点后统一迁移和更新；旧节点仅在单根域兼容缺省根字段，多根域缺少明确绑定时拒绝操作，不能依赖混合版本节点运行。隔离恢复将应用服务停用并增加修订，不能直接恢复认证。

【涉及其他业务】同一工程内复用审批执行、审计范围与检查点逻辑；既有 HMAC、H5 不切换到本协议。应运行完整 PostgreSQL race、故障与 Web 集成测试及浏览器发布验证。没有修改其他仓库业务。

开发安全验收不代表生产验收。离线签发隔离、独立恢复分发、硬件托管、防回滚存储、真实网络和数据库故障切换、渗透测试仍需生产前验收。
